## 一、已验证事实（本会话成功读取的公开网页）

以下内容来自本会话中成功读取的三个公开网页，属于可引用的已验证事实。

### 1. OneAPI（songquanpeng/one-api）— 开源中转/网关

- **核心定位**：LLM API 管理与分发系统（即"中转站"），统一 API 适配，可用于 key 管理与二次分发。
- **支持的供应商**：OpenAI、Azure、Anthropic Claude、Google Gemini、DeepSeek、字节豆包、ChatGLM、文心一言、讯飞星火、通义千问、360 智脑、腾讯混元等主流模型。
- **部署形态**：单可执行文件，提供 Docker 镜像，一键部署，开箱即用；提供英文 UI。
- **技术要点**：支持以负载均衡方式使用多个渠道（channel）；支持从 .env 文件读取环境变量（示例见 .env.example）；设置 REDIS_CONN_STRING 后使用 Redis 作为缓存（官方提示：若数据库访问延迟很低则不必启用 Redis，启用后可能出现数据滞后）。
- **来源**：https://github.com/songquanpeng/one-api

### 2. LiteLLM Proxy（BerriAI/litellm）— 开源 AI 网关

- **核心定位**：AI Gateway（AI 网关），Rust 核心 + Python SDK。
- **能力**：以 OpenAI 格式（或原生格式）调用 100+ 家 LLM API；内置成本追踪、guardrails（护栏）、负载均衡、日志功能。
- **支持的供应商**：Bedrock、Azure、OpenAI、Anthropic、VertexAI、vLLM、Nvidia NIM 等。
- **新特性（MCP Gateway）**：可将 MCP Server 接入网关，再通过 /chat/completions 接口调用 MCP 工具——即网关层开始向 Agent/MCP 生态延伸。
- **来源**：https://github.com/BerriAI/litellm

### 3. OpenRouter — 商业聚合平台

- **核心定位**：统一接口（The Unified Interface），面向全球用户的商业模型聚合服务。
- **公开数据**：月 token 消耗 300T+、全球用户 1000 万+、80+ 供应商、500+ 模型；支持文本、图像、视频、音频。
- **功能亮点**：多供应商故障转移（某供应商故障时回退到其他供应商）；价格与性能对比透明化；边缘部署以降低延迟；支持自定义数据策略（限制 prompt 只流向受信任的模型与供应商）。
- **来源**：https://openrouter.ai

## 三、市场格局初步判断（推断/观点）

基于已验证事实与一般知识，可形成以下初步框架（均为推断，需后续数据支撑）：

1. **三类玩家并存**：
   - **开源自部署网关**：OneAPI、New API、LiteLLM Proxy。特点是可自托管、渠道管理灵活、成本可控，适合个人/小团队自建"中转"。
   - **商业聚合平台**：OpenRouter（已验证）、硅基流动（推断）。特点是开箱即用、多模型统一入口、按量付费，靠聚合与转售赚取差价或服务费。
   - **云厂商托管平台**：火山方舟、阿里云百炼、腾讯云 TI、AWS Bedrock、Azure OpenAI。特点是官方模型托管、合规与安全背书、与企业云生态绑定，通常不涉及"转售第三方模型"的灰色地带。

2. **开源网关与商业聚合的差异**：开源网关把"渠道配置、负载均衡、key 管理"下放给使用者（自担供应商对接与合规责任）；商业聚合把这一切封装为服务（平台承担供应商管理与故障转移，如 OpenRouter 的 fallback 机制）。

3. **统一协议趋势**：已验证事实显示 LiteLLM 与 OpenRouter 均以"OpenAI 兼容格式"作为统一入口，说明 OpenAI 兼容协议事实上已成为中转/聚合层的通用标准。

4. **生态延伸**：LiteLLM 已出现 MCP Gateway（通过 chat/completions 调用 MCP 工具），提示中转层正从"模型路由"向"工具/Agent 路由"演进。
