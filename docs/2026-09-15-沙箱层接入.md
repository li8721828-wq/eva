# Eva 沙箱层（OS-Level Sandbox）接入

日期：2026-09-15  
发布版本：待定（沿用 0.1.206）  
目标平台：跨平台

## 更新背景

Codex harness 在 macOS 上用 `sandbox-exec`、Linux 上用 `bwrap`（bubblewrap）、Windows 上用 AppContainer，实现每次命令调用的操作系统级隔离。Eva 在此之前没有对应的层——"工具审批"只是用户确认，批准后工具仍然以主进程权限裸跑。

本次补齐沙箱层，让审批策略在"批准"之后仍有 OS 级的强制约束。

## 一、设计原则

### 审批策略 ≠ 沙箱策略

两者独立、正交组合：

| 审批策略 | 效果 |
| --- | --- |
| `off` | 不弹审批卡，全靠沙箱 |
| `safe` | 写入/终端/浏览器工具弹卡，沙箱协同 |
| `strict` | 读取也弹卡，沙箱协同 |
| `paranoid` | 每次都弹卡 |

| 沙箱等级 | 效果 |
| --- | --- |
| `off` | 无 OS 层限制，审批卡是唯一保护 |
| `permissive` | 沙箱存在，workspace + grants 允许读写；危险命令被拦截 |
| `strict` | 默认拒绝；仅 workspace + Eva cache + /tmp 可读写；网络可选禁 |

**强制组合规则**：沙箱 `off` 时审批策略不变；非 `off` 沙箱时，审批策略 `off` 升级为 `safe`，确保用户知情。

### 接入方式

- `AgentRunner.run()` 开始时通过 `openSandboxScope()` 注册本 run 的沙箱上下文（`services/sandbox/scope.ts`），结束时 `closeSandboxScope()`（finally）
- 并发 run 各自持有作用域，读取方（`FileService`、`TerminalService`）在每次判定时调用 `currentSandboxScope()` 取当前最严格的一档；不再使用模块级单例 setter
- 提交终端命令（`write_terminal` 的 `submitted` 分支）必须自行调用 `checkSandboxCommand()` 判定，因为 `writeInput` 也被面板的原始按键复用

> 注：2026-09-22 起，原 `TerminalService.setSandboxContext` / `FileService` 模块级 setter 已被按 run 的作用域注册表取代（详见 `docs/project-memory/CHANGELOG.md`）。


## 三、跨平台实现

### macOS（`DarwinSandboxExecBackend`）

`node-pty.spawn` 的 shell 进程用 `sandbox-exec -p <profile> <shell> <args>` 包装。`profile` 包含：

- `(version 1)(deny default)`：默认拒绝
- 允许读取系统路径（`/usr/lib`、`/bin` 等）
- `allowNetwork` 控制 `(allow network*)`
- workspace + `extraAllowedPaths` 允许读写
- Eva cache 目录允许读写

`sandbox-exec` 随 macOS 内核提供，`probe()` 检查可执行性。

### Linux（`LinuxBubblewrapBackend`）

`bwrap`（bubblewrap）不在大多数发行版预装。`probe()` 用 `bwrap --version` 检查，找不到时 `available=false`。

包装方式：`bwrap <args> -- <shell> <args>`，其中 args 包括 `--unshare-user-try --unshare-pid --ro-bind /usr /usr` 等。`--unshare-net` 控制网络隔离。

### Windows（`Win32SandboxBackend`，v1）

v1 纯 JS 实现，无 OS 级进程包装（`AppContainer` / Job Objects 需要 native 绑定）：

- `evaluateCommand`：灾难性命令正则拦截（`rm -rf /`、`format`、PowerShell 危险 cmdlet 等）
- `evaluatePath`：目标路径必须在 workspace + grants + 系统允许列表内
- `wrap()`：原样返回 argv，供调试

**v2 待办**：通过 `@anthropic-ai/sandbox-runtime` 或 napi-rs Rust helper 调用 Win32 AppContainer API。

## 四、接入点

### TerminalService（`executeCommand`）

每次命令执行前调用 `evaluateSandboxCommand(commandLine, context)`：
- `off` → 直接放行
- `permissive/strict` → 灾难性命令拦截，返回 `exitCode=126` + 拒绝原因

`createSession`（shell 启动）时，若 `sandboxContext.level !== 'off'`，用 `wrapCommandForSandbox()` 包装 shell 的 `node-pty.spawn` argv（macOS `sandbox-exec` / Linux `bwrap`）。

### FileService（`writeFile` / `writeBuffer`）

在 `normalizeAndValidate` 完成后、第一次 `fs.promises.writeFile` 调用前，调用 `evaluateSandboxPath(resolved, 'write', context)`。路径被拒时抛出 `Error(decision.reason)`，在 `agent-runner.ts` 的 `executeToolInternal` 捕获并返回 `isError: true` 结果。

### 读写分离

- **写操作**：严格受 sandbox 限制（workspace + grants + extraAllowedPaths）
- **读操作**：workspace + grants + `readOnlyRoots()`（系统二进制、locale 等）
- `sandbox.level === 'off'`：无限制

## 七、已知限制与待办

- **Windows v2**：需要 native 绑定才能实现真正的 OS 进程隔离。当前为"最佳努力"JS 层校验，不具备 `sandbox-exec` / `bwrap` 的强制效力。
- **macOS / Linux 二进制缺失**：若 `sandbox-exec` / `bwrap` 不在 PATH，`available=false`，但应用不阻止运行——用户会在 Settings 看到警告。
- **`fileAccessGrants` 未参与沙箱路径决策**：当前 `SandboxContext.fileAccessGrants` 结构已定义，但 `evaluatePath` 只用了 `workspacePath` 和 `extraAllowedPaths`。需要在路径决策中引入 grants。
- **日志轮转**：`AgentRunEventStore` 和沙箱 profile 都会随时间积累；后续按日期归档。
- **MCP 工具**：沙箱目前不覆盖 `mcp__*` 工具的内部调用（MCP 服务器独立进程）。
