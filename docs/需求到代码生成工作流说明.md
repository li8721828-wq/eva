# Eva：从需求到确定性代码生成的工作流

## 1. 目标与边界

该工作流将一项业务需求依次沉淀为需求模型、实施规格、领域 DSL 和可验证的代码生成包：

```text
/requirement
  -> /requirement-modeling
  -> /spec
  -> /dsl
  -> /coding
```

前四个阶段可以使用模型完成分析、建模、规格与领域语言表达；从 DSL 进入 `/coding` 后，流程不再调用任何模型或供应商接口。DSL 之后的解析、校验、IR 转换、Java 生成与编译验证均由本地确定性程序完成。

`/coding` 生成的是隔离的代码包，不会直接写入或覆盖业务模块。将生成包合入生产模块仍需要经过物理目标模型、交付计划和审批。

## 2. 使用前准备

### 2.1 工作区

对话必须关联到目标项目工作区。每次 `/requirement` 都会创建独立 RMSD（Requirement Modeling, Specification, DSL, Coding）需求包：

```text
<workspace>/
  .eva/
    RMSD/
      <需求名称>/
        runs/
          <run-id>/
            RMSD-STANDARD.md
            requirement/{upstream,intermediate,output}/
            requirement-modeling/{upstream,intermediate,output}/
            spec/{upstream,intermediate,output}/
            dsl/{upstream,intermediate,output}/
            coding/{upstream,intermediate,output}/
```

`<需求名称>` 优先由 `/requirement` 正文中的第一个有效业务标题或描述生成；正文未提供时使用附件文件名，不再使用对话标题。每次新建 `/requirement` 都在该名称下创建新的 `<run-id>` 目录，同名需求不会覆盖旧运行。只有同一轮澄清会继续更新当前运行目录。每个阶段的 `upstream` 只保存上游 `output` 快照，`intermediate` 保存分析和生成过程，`output` 只保留供下游消费的最终契约。每个阶段还包含 `ARTIFACT-CONTRACT.md`，明确文件格式、必须产物与输入边界。

### 2.2 运行条件

- `/requirement`、`/requirement-modeling`、`/spec`、`/dsl` 需要配置可用模型。
- `/coding` 不需要模型或 API Key，但需要工作区内的 `code-production-pipeline`。
- 当前确定性 Java 参考生成器还需要本机可执行的 `python.exe`、Python 的 YAML 依赖，以及 JDK 中的 `javac` 和 `java`。

### 2.3 两类持久化位置

Eva 会同时保留运行记录与工作区交付物：

| 位置 | 用途 |
| --- | --- |
| `%APPDATA%/eva/requirement-engineering/runs/<runId>/` | 内部运行档案，用于恢复、审计和界面展示。 |
| `<workspace>/.eva/RMSD/<需求名称>/runs/<run-id>/...` | 单次运行的项目内流水线包：需求、建模、规格、DSL、代码生成及其阶段契约。 |

运行记录不是聊天记录的替代品。下游阶段应读取固定路径的阶段产物，而不是从自然语言对话中猜测上游结论。

## 3. 阶段总览

| 阶段 | 命令 | 输入 | 可继续条件 | 主要输出 |
| --- | --- | --- | --- | --- |
| 需求分析 | `/requirement` | 业务描述和可选附件 | 澄清与评测达到门槛 | 原始输入、分析、代码证据、澄清、评测 |
| 需求建模 | `/requirement-modeling` | 已明确的需求 | 需求质量达到 80 分 | 建模计划、标准化需求模型、最终建模文档 |
| 实施规格 | `/spec` | 最终需求模型及代码证据 | 规格一致性达到 85 分 | 业务、行为、验收、追溯、校验及最终实施规格 |
| 领域 DSL | `/dsl` | 通过校验的最终实施规格 | 存在 `implementation-ready` 最终规格 | DSL 计划、领域语言模型、最终 DSL 文件 |
| 代码生成 | `/coding` | `domain-language.dsl` | DSL 阶段完成 | 语义 DSL、生成 IR、Java 包、编译验证报告 |

## 4. `/requirement`：需求分析、澄清与评测

### 用法

```text
/requirement 销售合同需要支持接收、变更、履约跟踪和回传结果。
```

也可以在输入框中先通过 `/file` 或 `/folder` 添加资料，再输入需求命令。附件应是业务需求、现有流程、规则或相关材料；它们会作为本轮需求输入的一部分。

### 处理过程

1. 保存原始需求文本和附件上下文。
2. 生成需求范围、业务行为、质量与边界分析。
3. 在工作区可用时收集代码结构和集成证据，但不会把实现细节转换成对用户的澄清问题。
4. 生成需要确认的澄清项，并在界面中等待选择。
5. 对完整性、可测试性和可行性进行评分。

### 结果与门槛

需求质量门槛为 `80`。达到门槛后，还必须通过一次独立的最终需求语义放行审计，运行状态才会成为 `ready-for-specification`，可以进入 `/requirement-modeling`。评测使用固定的 `READINESS` 与 `UNRESOLVED_ITEMS_JSON` 契约：模型按语义列出事实、影响、所需决策和是否阻塞，程序只校验该结构与阻塞状态，不依赖“待确认项”等文字写法。未达到门槛、审计结构缺失或仍有 `blocking=true` 项时，必须先完成澄清卡片中的选项，再继续该阶段。

## 5. `/requirement-modeling`：将需求变成可追溯模型

### 用法

```text
/requirement-modeling
```

该命令没有额外正文或附件。它只消费上一阶段已确认的最终需求，避免本轮临时消息改变建模输入。

### 处理过程与产物

Eva 会根据需求选择适用的建模表达，并生成：

- `modeling-plan`：采用哪些需求建模标准及原因。
- 若干标准化模型文档：例如 EARS、用例、流程、规则、数据或验收模型。
- `final-merged`：最终需求建模文档，是 `/spec` 的唯一建模输入。

对于当前 RMSD 需求包，`/spec` 从 `requirement-modeling/output/final-requirement-model.md` 读取建模成果，不依赖原始对话。旧版 `requirements/<需求包>/01-requirement-model/` 仅保留导入兼容。

## 6. `/spec`：构建并校验实施规格

### 用法

```text
/spec
```

命令只读取最终需求、最终建模和工作区代码证据；不要在命令后附加新需求，也不要携带附件。新信息应先回到 `/requirement` 或澄清阶段。

### 处理过程

1. 读取最终需求模型及可用代码证据。
2. 生成业务规格、代码对齐规格和追溯矩阵。
3. 执行一致性检测；如果检测发现阻塞项，会提供可选择的处置路径。
4. 用户处理阻塞项后，重新生成必要文档并再次校验。
5. 分数达到 `85/85` 后，生成 `implementation-ready` 最终实施规格。

### 固定产物

规格阶段最终输出在：

```text
<workspace>/.eva/RMSD/<需求名称>/runs/<run-id>/spec/output/
```

典型内容包括业务规格、行为规格、验收规格、状态机、规则与异常、权限、集成边界、追溯矩阵、校验记录和最终实施规格。

### 通过与未通过

- 通过：运行状态为 `ready-for-implementation`，可以执行 `/dsl`。
- 未通过：运行状态为 `awaiting-spec-resolution` 或回到 `ready-for-specification`；必须处理检测出的阻塞项后重新执行 `/spec`。
- 仅“执行过 `/spec`”不等于“通过 Spec”。只有一致性门槛通过并生成最终实施规格，才允许后续阶段。

### 当前识别限制

当前 `/dsl` 优先识别 Eva 运行记录中状态为 `ready-for-implementation` 且包含 `implementation-ready` 文档的 Spec 成果。已存在于工作区、但不是由当前运行记录创建的外部 Spec 发布包，即使它的 `spec-stage-release-manifest.md` 表示可进入 DSL，也可能尚未被 `/dsl` 自动导入。这是当前识别逻辑的限制，不代表该 Spec 本身未完成。

## 7. `/dsl`：从实施规格生成领域语言文件

### 用法

```text
/dsl
```

该命令必须在 Spec 已通过后运行，不接受本轮附件或图片。

### 输入边界

`/dsl` 使用最终实施规格及其支持性规格文档，生成领域层表达。它不应生成 Java、SQL、REST API、表结构或其他物理实现细节；未确认的业务事实必须被标记为 `OPEN`，不能靠猜测补齐。

### 固定产物

DSL 输出在：

```text
<workspace>/.eva/RMSD/<需求名称>/runs/<run-id>/dsl/
  upstream/implementation-specification.md
  intermediate/01-dsl-plan.md
  intermediate/02-domain-language.md
  output/domain-language.dsl
```

| 文件 | 内容 |
| --- | --- |
| `01-dsl-plan.md` | 领域、限界上下文、实体、命令、事件、规则和追溯项的生成计划。 |
| `02-domain-language.md` | 可评审的领域语言模型，包含术语、实体、属性、命令、事件、策略和未决项。 |
| `domain-language.dsl` | 最终机器可消费 DSL；第一行是 `domain <Name>`，随后是 `entity`、`command`、`event` 和 `rule` 等稳定语法。 |

`domain-language.dsl` 是 `/coding` 的唯一业务输入。

## 8. `/coding`：纯确定性代码生成

### 用法

```text
/coding
```

执行前必须完成 `/dsl`。该命令拒绝本轮附件与图片，也不读取聊天内容，不调用模型、不请求 API。

### 确定性处理链

```text
domain-language.dsl
  -> 语法解析与实体提取
  -> 语义 DSL 包
  -> validate_semantic_dsl.py
  -> dsl_to_generation_ir.py
  -> validate_generation_ir.py
  -> generic_semantic_java_adapter.py
  -> verify_generic_semantic_java_output.py
```

生成器会把 DSL 的 `entity` 块转换为带有稳定 `DSL-*`、`GEN-*`、`CODE-*`、`TEST-*` 追溯标识的语义包和生成 IR。随后调用本地 Java 参考适配器，输出隔离的 Java 目录并通过 `javac` 与生成的契约测试验证。

### 输出路径与目录

输出路径由 DSL 内容的 SHA-256 决定：

```text
<workspace>/.eva/RMSD/<需求名称>/runs/<run-id>/coding/output/runs/<DSL-SHA256>/
  00-input/
    domain-language.dsl
  01-semantic-dsl/
    dsl-manifest.yaml
    domain.yaml
    state-machine.yaml
    rules.yaml
    authorization.yaml
    integration.yaml
    generation-map.yaml
  02-generation-ir/
    target-model.yaml
    generation-ir.yaml
  03-generated-code/
    generation-result.yaml
    src/main/java/...
    src/test/java/...
  04-verification/
    verification.md
  codegen-manifest.json
```

| 文件或目录 | 用途 |
| --- | --- |
| `00-input` | DSL 输入快照，用于证明生成输入未被篡改。 |
| `01-semantic-dsl` | 从最终 DSL 确定性转换的语义包；包含输入哈希和开放项门禁。 |
| `02-generation-ir` | 生成器可消费的中间表示，明确声明 `ai_involvement: none`。 |
| `03-generated-code` | 隔离的 Java 源码、测试源码和 `generation-result.yaml`。 |
| `04-verification` | 校验、IR 转换、生成和 Java 编译测试的执行结果。 |
| `codegen-manifest.json` | 输入 DSL 哈希、输出路径、适配器和完成状态。 |

### 幂等与安全行为

- 相同 DSL 内容始终映射到相同的输出目录。
- 如果该目录已有完成状态且输入哈希相同，`/coding` 直接复用已验证结果。
- DSL 改变后，哈希改变，生成新的目录；旧生成包保留以便审计与比较。
- 生成器拒绝覆盖非空的生成目录，也不会写入业务模块。
- 当前使用的是非生产 Java 参考适配器。生产级实体、Mapper、SQL、Controller 或数据库迁移，需要先提供已审批的物理目标模型，再走受控交付流程。

## 9. 常见问题与排查

### 9.1 “没有已完成的需求建模成果”

确认当前对话已绑定正确工作区，并检查：

```text
.eva/RMSD/<需求名称>/runs/<run-id>/requirement-modeling/output/
```

是否存在可读取的建模文档。若需求分析仍在等待澄清，先完成澄清再执行 `/requirement-modeling`。

### 9.2 “没有通过 /spec 的最终实施规格”

先在需求面板检查当前运行的状态、规格评分和阻塞项。只有校验达到门槛并生成 `implementation-ready` 才能进入 `/dsl`。如果工作区已有外部 Spec 发布包却仍报该错误，参见第 6 节的“当前识别限制”。

### 9.3 `/dsl` 或 `/coding` 显示 “No handler registered”

这是桌面应用运行着旧主进程的表现。关闭 Eva 后重新从快捷方式启动；仅刷新页面不会重载 Electron 主进程的 IPC handler。

### 9.4 `/coding` 失败

依次检查：

1. `dsl/output/domain-language.dsl` 是否存在且包含至少一个 `entity <Name> { ... }` 块。
2. 工作区是否包含 `code-production-pipeline`。
3. `python.exe`、PyYAML、`javac` 和 `java` 是否可执行。
4. `coding/output/runs/<DSL-SHA256>/04-verification/verification.md` 中的具体错误。

## 10. 推荐操作顺序

```text
1. 选择项目工作区。
2. /requirement <业务需求>，完成澄清。
3. /requirement-modeling，确认最终建模。
4. /spec，处理所有规格阻塞项，直到通过。
5. /dsl，检查 dsl/upstream、dsl/intermediate 与 dsl/output。
6. /coding，查看 coding/output 中的 IR、Java 代码与验证报告。
7. 对生成包进行评审；生产合入另走审批和受控交付。
```

不要跳过评分与门禁。它们的目的不是阻碍生成，而是保证每一份 DSL 与代码都能回溯到已确认的需求和规格证据。
