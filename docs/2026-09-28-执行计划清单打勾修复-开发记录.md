# 执行计划清单打勾修复：提示词自相矛盾与界面「未逐项汇报」兜底

- 日期：2026-09-28
- 版本 / 分支：Eva 0.1.206，`develop`（HEAD `58fcdd2`）
- 状态：改动已完成并通过窄测与全量测试，**当日未提交**；运行中 Eva 的实测未做（见遗留事项）

## 一、背景与变更范围

用户在真机使用「详细过程输出」时发现：Agent 执行完一个步骤后，回复气泡里的执行计划清单和右侧任务便签都停在 `0/3`，一条也没打勾。这属于「界面声称的进度与真实进度不一致」，比不显示进度更糟，因为用户会据此判断任务卡住了。

本次改动集中在三处：派生层新增一个证据字段、渲染层新增一个诚实的空状态、提示词层消除一条自相矛盾的约束。涉及源码与测试 4 个文件，工程记忆 2 个文件；`src/main/agent-engine/context.ts` 当日上下午各改一次，本文档只写上午属于本主题的两条。

## 二、现象与风险

- 现象：模型正常发出了 `<eva-progress kind="plan">` 三行计划，界面正确渲染出三行清单，但直到该轮结束，`done` 始终为 0；`step` 汇报一条都没有。
- 风险：`0/3` 是一个**事实陈述**——它宣称「三件事都没做完」。而真实情况是「模型没有逐项汇报」，两者不能混为一谈。把后者显示成前者，会把一个正常完成的回复渲染成失败。
- 同一份派生结果同时喂给桌面气泡、右侧任务便签和 ACP 的 `plan` 快照（都走 `src/shared/plan-checklist.ts` 这一个来源），所以这个误判会同时出现在三个界面上。

## 三、排查：先排除派生与解析

在动手之前先把两条嫌疑路径各自证明无罪，避免「猜一个改一个」：

1. 把该轮落盘的 `progressUpdates` 原样喂进 `buildPlanChecklist`，条目能正常推进、能正常打勾——派生层无罪。
2. `TurnProgressProjector`（`src/main/ipc/progress-protocol.ts`）对 `item="N"` 属性的解析照常命中——解析层无罪。
3. 再看该轮实际收到的标签序列：只有一个 `plan`，之后**一条 `step` 都没有**。

结论：链路没问题，是模型根本没汇报。问题在提示词。

## 四、根因：`context.ts` 里两条规则互相矛盾

`src/main/agent-engine/context.ts:423` 的自适应回复约束原文（修复前）写着：不要添加执行更新（execution updates）、发现、验证、风险和下一步，除非确实相关。而紧邻其后的 `detailed` 分支要求：先出计划，再逐条 `step` 汇报。

两条规则给了模型一个无解的指令对：`<eva-progress>` 汇报正是「执行更新」。模型采纳了前面那句「不要添加」，于是发出了计划就收声——这恰好解释了「有清单、零打勾」这个特定形态：`plan` 被当作正文的一部分发了出去，后续的过程汇报被同一条规则抑制了。

## 五、修复

1. **约束限定作用域**（`context.ts:423`）：把「不要添加执行更新……」显式限定为「这是针对回复本身的段落，**永不豁免下方 `<eva-progress>` 汇报规则**」。两条规则不再打架。
2. **计划即承诺**（`context.ts:441`）：新增一条——开了计划就要逐行汇报，调研与解释类工作同样算步骤（读相关文件、形成结论即是步骤）；不打算逐行汇报，就不要以计划开场。
3. **新增证据字段 `stepReportCount`**（`src/shared/plan-checklist.ts:34`、`60`、`69`、`73`、`84`）：统计自当前 `plan` 块以来实际收到的 `step` 汇报条数。越界（没有任何条目可勾时到达）的 `step` 同样计入，因为它们确实是真实汇报；遇到新的 `plan` 块重置为 0，因为步骤编号从那里重新开始。
4. **界面空状态改为诚实文案**（`src/renderer/components/chat/PlanChecklist.tsx:32`、`38`）：当 `!streaming && stepReportCount === 0` 时，计数位显示「未逐项汇报」而不是 `0/N`，条目保持未勾。复用既有 `.plan-checklist__count` 样式（`index.css:552`），无新增 CSS。
5. **明确不做的一件事**：不按工具调用数自动打勾。那是把执行证据伪造进清单，既违反本仓库「打勾必须有可指向的依据」的既有约束，也违反既定的反硬编码取向。缺证据就如实显示缺证据，而不是造一个好看的进度。

区分清楚了三种状态：`stepReportCount === 0` 是「没汇报」，`stepReportCount > 0 且 done < total` 是「做了但没做完」，`done === total` 才是完成。之前这两态被压成了同一个 `0/N`。

## 八、使用注意

- 「未逐项汇报」只在该轮结束（`!streaming`）且一条 `step` 都没收到时出现。流式过程中仍是 `0/N`，这是刻意的：那一刻确实还没勾上任何一条。
- 这条兜底不改变打勾语义。只有 `step` 汇报能勾上条目，重复叙述计划某一行不构成完成。
- ACP 侧目前仍只把 `done` 派生成 `plan` 快照的条目状态，`stepReportCount === 0` 这一区分**没有**传给终端，手机端暂时看不到「未逐项汇报」。
