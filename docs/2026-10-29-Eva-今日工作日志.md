## 二、程序化 Skill：从「文本」到「可执行能力」

**动因**：Skill 之前只是提示词资产。想让它真正「按团队规范干活」，模型必须能执行 Skill 里的东西，而一旦能执行，就要能回答「谁允许它执行、它能碰什么」。

**边界是怎么画的**（这是这块工作的重点，不是「加一个执行工具」）：

- 命令、解释器、入口文件**全部来自 `SKILL.md` 声明**，工具参数里没有 command 字符串——模型只能选「跑哪一条」并填声明过的 `{placeholder}`，不能临时拼命令。
- 执行前七步校验：Skill 存在且启用 → 命令已声明 → 参数只允许声明过的槽位（拒绝 shell 元字符、前导 `-`、`..`、盘符、超长）→ 目录与入口重新 `realpath` 且必须在 Skill 目录内、非目录、非二进制 → 当前 Agent 的沙箱判定 → `spawn(argv, { shell: false })`。
- 每次运行把入口复制到临时目录再执行，跑完即删——**运行中的脚本改不了下次要跑的代码**；`cwd` 固定为 Skill 目录；超时取消 + `SIGKILL`；stdout/stderr 各截断 10000 字符。
- `run_skill_command` 归入 `terminal-command` 审批类别：`approval: none` 只影响声明意图与展示，**不绕过全局审批策略**。

**验证**：`skill-run.test.ts` 用真实 `node` 进程跑通成功执行、非零退出、200ms 超时终止、「运行中改写入口不影响磁盘副本」，以及沙箱边界（strict 下可跑、被拒规则在 spawn 前返回、模型参数不能越出 Skill 目录）。

**遗留**：沙箱判定只覆盖 `evaluateCommand`（危险命令黑名单 + 平台路径启发），没有包一层 OS 级隔离；`approval: none` 尚未提供「让用户按 Skill 免问」的入口；界面还没有「运行」按钮，只能经模型调用。

## 三、代码生成：1 个写死实现 → 4 个目标的插件注册表

**动因**：`/coding` 之前只有一个写死的 `builtin-java-reference`，想换目标必须改流水线；更糟的是 DSL 里写了未知字段类型会被**静默**当成 `String`，生成的代码看着能跑、语义已经错了。

**做法**：定一个 `CodeGenerator` 纯函数契约（`id` / `label` / `target` / `outputKind` / `capabilities` / `options` / `generate`），注册表提供 `getCodeGenerator` / `resolveCodeGenerator` / `validateGeneratorOptions`。已注册 4 个：

- `java-reference`：字节输出与重构前完全一致（磁盘上已有的 content-addressed 包仍验证通过）
- `java-maven`：Maven 目录树 + `pom.xml` + 每实体单测，选项 `useRecords` / `nativeTypes`
- `json-schema`：draft 2020-12，`production`
- `sql-ddl`：PostgreSQL DDL，标 `migration-approval`（涉及库变更要单独审批）

`/coding` 从 `<intermediate>/02-generation-ir/target-model.yaml` 读批准声明：**文件缺失才写默认**（默认值显式写死为 `java-reference`，而不是「取第一个注册的」）；文件存在但不是 JSON、`generator` 不存在、`options` 有未声明键或非法值、`production_output: true` 但生成器是 `reference`、`output_kind` 与生成器不一致——**五种情况全部整轮失败**，不回落到默认。

**过程中踩到并修掉的六个问题**（这些比新增功能更值得记）：

1. 验证器原来拿 `generated` 里的名字去比文件名，但 SQL / JSON Schema 存的是构件名（`sales_orders`、`Invoice`）→ 改成「adapter 一致 + `generated` 非空 + 包内除 `generation-result.yaml` 外还有文件」。
2. `defaultTargetModel` 手改后字段丢失或重复 → 补回 `approvalStatus`。
3. `readTargetModel` 只读 camelCase，snake_case 写法的 target model 往返后丢字段 → 加 `stringField(camel, snake)`，`options` 兼容 `settings`。
4. JSON Schema 生成器曾把 `required` 当非法属性名——但 `required` 是合法字段名（`$ref` 才是 DSL 词法过不去的）→ 收窄为只对**实体名**做 `RESERVED_DEFINITION_NAMES`。
5. 同名产物字节不同时必须拒绝（`Existing deterministic artifact differs`）；越界路径 `../x` 在 `writeGeneratedPackage` 被拒。
6. 未知类型不再退化为 `String`，直接报错并列出可用集合；`decimal` 的 Java 落点由 `double` 改为 `java.math.BigDecimal`（有意变更，精度语义）。

**验证**：`deterministic-coding-service.test.ts` 从 4 项扩到 36 项，覆盖「同一 DSL 两次输出字节相同」、四个生成器各自通过 verification、选项拼写/取值被拒、target model 五种拒绝路径、`java-reference` 字节兼容（固定文本断言）、越界写入被拒、空包（只有 result）不通过验证。

**遗留**：验证是结构性的，不编译也不跑 `mvn`/`javac`；`sql-ddl` 是 PostgreSQL 方言（MySQL 需另写生成器，不要把方言差异塞进 option）；`generated` 里存的是构件名而非文件名，前端若要展示文件列表应读目录；`/coding` 的复用检查仍只比 `status` + `sourceDslSha256`，**不比 generator**——同一 DSL 换 target model 会命中复用分支。

## 五、今天的结论

1. **契约优先于措辞**。无论是 Skill 的参数槽位还是流水线的就绪标记，能被程序判定的东西就不要交给「模型自我评价」。今天所有新增的质量保证都落在这条上。
2. **边界要写进声明，不要写进提示词**。Skill 的命令、解释器、入口全部来自 `SKILL.md`，模型只有「选择权」；target model 必须显式批准，生成器不能自行升格为生产。
3. **「可复现」比「更聪明」更好卖**。对交付场景来说，同一 DSL 必然产出同一字节，比多生成两行漂亮代码更有说服力——这也是方案设计书里最硬的一条。
