## 一、两条通道各自要解决的事

**技能选取。** 他的原话：「那个skill技能，我要求可以按住/可以加载出来已经安装的skill，然后配上提示词，可以使用这个技能」。此前技能只有一条被动路径——模型在常驻目录里自己命中后调 `load_skill`；用户没有手动点用的入口（设置页 `SkillPanel` 只能开关与重扫）。三个产品决定由他选定：主进程直接注入本轮提示、只作用于下一条消息、同一个 `/` 面板分两组（命令 + 技能）。

**ask_user。** 他的原话：「我想让eva在询问用户的意向或者出选项的时候，可以出一个可以选择选项的卡片式的东西，这样用户去点击就行了，不然这样用户还得一个个输入选项很麻烦」（附截图：Eva 正文里列 1/2/3 加子选项）。Eva 此前只能用正文模拟选择控件，用户要手打「选第二个」。三个档位由他选定：点完**原地续跑**（不另起一轮）、**一卡一问**（不要确认按钮这多出来的一层）、**桌面 + 专家团 + app-server 三个表面都要**（Wave 1 只落了桌面，见第九节）。

## 二、技能选取：`/` 面板 + 单轮注入

- **面板**。`chat-commands.ts:24` 的触发正则放宽到 `/^\/([a-z0-9._-]*)$/i`（技能名允许 `.` 与 `_`）；`buildSlashPopoverItems`（`:34`）返回「命令在前、技能在后」的平铺列表，共用一个 `activeCommandIndex` 走方向键与 Tab；技能与命令重名时列两行（命令在前），按索引选中不含糊。
- **清单按会话取**。新通道 `SKILL_INVENTORY_FOR_CONVERSATION`（`ipc-channels.ts:76`，handler `ipc/skill.ts:22`）在**主进程**按 conversationId 解析工作区路径并过滤 `enabled`；渲染层无从列出被禁技能。不拓宽 `SKILL_LIST` 是因为后者收渲染层裸 `workspacePath`，`SkillPanel.tsx` 依赖其现有契约（渲染层没有 workspaces 列表）。
- **取正文复用 `loadSkill`**。`buildSelectedSkillContext`（`skill-service.ts:221`）只加一层框式：`--- Skill selected by the user: <name> ---` + 一句「用户为本轮显式选中」说明 + 正文 + `--- End skill ---`（仿 `document-attachment-service.ts:100` 既有约定）。`load_skill` 本体一字未改，模型自选与用户点选并存，不存在第二份正文来源。
- **只作用一条是结构保证**。正文只进本轮 `runnerMessage.attachmentContext`；`conversation.ts:874-897` 把 `skillName` 读自 payload、落盘行只带 `attachedSkillName`（供徽标显示），`convStore.addMessage` 的 payload 永不含正文——因此不依赖 `PRIOR_ATTACHMENT_CONTEXT_MAX_CHARS = 2_000` 的压缩路径。
- **选中不写 `inputText`**。紫色高亮叠层从 `inputText` 推导，写进去会让 `/技能名` 漏进消息正文，故改走 store 草稿态 `attachedSkill`（`use-chat-store.ts:68`）+ 输入框上方 chip（`InputBar.tsx:642`）；换会话清（`:158`）、发送同批清（`:574`）；空输入按 Backspace 清 chip（`InputBar.tsx:483`）；用户气泡挂「本次选用技能 X」徽标（`MessageBubble.tsx:650`）。
- **取不到技能（未知名/已被关掉）→ 回 `error` 事件并中止本轮发送**，不静默降级成「没带技能也发出去」。
- **与需求命令互斥**：`/requirement|/requirement-modeling|/spec|/dsl|/coding`、Symposium、专家团这些路径都不经 `chat.send`，各自清掉 chip，不半生效。
- **不动 `systemPromptSuffix` 与目录构建**，供应商 prompt cache 前缀照旧逐字稳定。

## 三、ask_user：判定权在模型、能力不是授权

- **没有新造机制**，整条通道照抄工具审批那一套：主进程挂 Promise → `chat:stream` 推 `ask_user_request` 事件 → 渲染层出卡 → `chat:ask-user:decide`（`ipc-channels.ts:109`、preload `decideAskUser` `:370`）invoke 回来 → 唤醒同一个 Promise。可行前提是 `ToolDispatcher.dispatch()` 本来就在 `tool.execute()` 之前 await `requestToolApproval` 递过来的 Promise（`tool-dispatcher.ts:137-149`）。
- **判定权在模型、不在关键词**：只加工具描述（何时该用/不该用），不做任何「正文里有问号就出卡」的解析；护栏明写不许用正则从正文猜「这是在提问」。
- **能力不是授权**：`ask_user` 不进任何智能体的工具勾选清单也能用——`isToolAllowed` 里给它开豁免（`tool-dispatcher.ts:92`，对齐 `manage_personal_preferences` 的既有隐式暴露写法）；但它**只在有 `requestUserChoice` 通道的运行里暴露**（`agent-runner.ts:383` 的定义暴露门），没人在另一头的运行根本看不到这个工具。
- **无通道即报错、绝不挂起**：`execute()` 在 `context.requestUserChoice` 缺失时直接抛「请改用正文文字提问」（`ask-user-tools.ts:41-43`）——挂一个永远不会来的点击比模型自己打字更糟。
- **参数校验前置**：2–6 项、question ≤200 字、label ≤40 字、label 去重、detail 截到 160 字（`ask-user-tools.ts:3-8`）；不合规时模型自己重试，不出半张卡。
- **单卡队列**：每会话同时只允许一张卡（`presentAskUser`，`ask-user-policy.ts:47`）——并行工具批次里若让后到的卡覆盖渲染层状态，先到的那张就再也点不到。
- **跨会话防串**：decide 必须带 `conversationId` 且与挂起记录相符才落地（`resolvePendingAskUser`，`:87`）；渲染层对已结束回合的卡片直接丢弃、`accepted=false` 也清卡（`use-chat-store.ts:662-674`），不留点不动的死卡。
- **作废点**：新发送（`conversation.ts:767`，理由「用户改发了新消息」）与 abort（`:1695`，理由「用户停止了本次回答」）连同挂起的卡一起作废。
- **超时 5 分钟**（`ASK_USER_TIMEOUT_MS`，`ask-user-policy.ts:22`）自动作废并把「等待超时」回填给模型；挂起态**只在内存**（与审批一致），应用重载即丢。
- **卡片零 chrome 是他的界面规矩**：问题即标题、选项即控件、`detail` 只进 hover 的 `title`；没有「请选择：」这类可见标签、没有弹层中间层、没有确认按钮。因此这张卡没有任何需要进 `ui-copy` 的自造文案。
- 四份名单都补齐：`shared/tool-catalog.ts:30`（`category: 'Integrations'`, `risk: 'read'`）、`tool-approval-policy.ts:31` 的 `READ_ONLY_TOOLS`、dispatcher 白名单豁免、`tools/index.ts:192` 注册（`ToolContext.requestUserChoice` 定义在 `:42`）。
