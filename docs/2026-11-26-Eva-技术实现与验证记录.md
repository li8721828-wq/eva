## 二、权限快照与审批生命周期（0.1.234）

### 1. 权限变化结束旧运行

[conversation-permissions.ts](../src/shared/conversation-permissions.ts) 定义有效权限变化判据。[ConversationLifecycleService](../src/main/services/conversation-lifecycle-service.ts) 在权限保存成功后通知宿主，停止旧快照下的聊天、子任务、团队、目标与排队执行，清除临时审批并发布 `permissions_changed`。

普通标题等元数据变化、相同授权及授权排序变化不触发该流程。保存失败不发布权限变化事件。原正文和工具记录保留；下一次用户请求使用新权限，不自动重放已经发生的副作用。

### 2. 唯一审批期限与卡片

[ToolApprovalCard.tsx](../src/renderer/components/chat/ToolApprovalCard.tsx) 由输入框上方等待区承载。主进程在实际展示请求时设置 `requestedAt/expiresAt`，并以审批 ID 发布关闭事件。前端显示实际期限，不在挂载时重启计时，不因倒计时归零自行拒绝，也不能用旧事件关闭新卡片。

[tool-approval-policy.ts](../src/main/services/tool-approval-policy.ts) 在单次运行中记录同一操作的超时/拒绝结果，排队请求也复核，阻止通过更换调用 ID 或同目标内容不断重复审批。不同目标、新轮次及取消清理仍独立。

[tool-failure.ts](../src/shared/tool-failure.ts) 为审批超时、拒绝、访问、路径与编辑冲突提供分类，同时保留原始错误。审批超时不伪装成可自动重试的 I/O 超时；未知 SDK 错误不强行归类为已知原因。

## 三、运行时工具隔离（0.1.235）

### 1. 移除原生运行时中的 Eva 工具执行通道

[native-engine-runner.ts](../src/main/agent-engine/native-engine-runner.ts) 与原生 worker 不再向 Pi/Harness 注册 Eva/MCP/业务扩展，也不保留原生失败后调用 Eva 核心执行器的回退通道。

| 后端 | 实际工具与执行归属 |
| --- | --- |
| Eva | Eva 工具注册、已启用扩展及原执行策略 |
| Pi | Pi SDK 的 read/write/edit/ls 与平台 shell |
| DeepSeek Harness | DSH read/read_image/write/edit、pwsh/bash 与启用的原生 todo/goal；目录搜索通过已启用 shell |

[pi.mjs](../resources/execution-engines/pi.mjs) 和 [harness.mjs](../resources/execution-engines/harness.mjs) 删除自动扩展注册与 `bridge.rpc('extension')` 路径。当前没有额外装载 DSH 独立目录/搜索插件；终端未启用时也不会补入 Eva 搜索能力。

宿主仍管理模型连接、密钥、权限、审批、沙箱、事件与上层任务。独立界面功能和需求斜杠命令并不因此全部改由原生工具执行。完整边界见[运行时工具边界](运行时工具边界.md)。

### 2. 会话配置代次

[native-session.ts](../src/main/agent-engine/native-session.ts) 使用 `toolProfile: runtime-only-v1` 区分配置。旧混合工具日志保留，后续创建新代次，并导入本次提供的全部聊天参考；不只取旧游标后的增量，也不重放历史操作。

历史工具标签保留事实。新轮次请求旧工具名时拒绝并显示当前未启用，不把历史记录改写为原生调用。SDK 内部状态不伪装为已完整恢复。

## 四、字体、玻璃材质与画布（0.1.236—0.1.237）

### 1. 阅读材质与字形

[conversation-reading.css](../src/renderer/styles/conversation-reading.css) 统一表格、代码块的玻璃表面：浅色白色底填充 alpha 为 `.18`，深色为 `.035`，使用细高光、14px 背景模糊及轻接触阴影。代码正文底层保持透明，表头与行色低遮盖，避免纯白面板割裂画布。

默认内置 Noto Sans SC Variable 5.3.1 的 101 个未改字节的 Unicode woff2 子集，正文字重 450、标题/强调 600；浅色墨色 `#424450`，深色 `#d2d4dd`。不启用合成字重，不覆盖用户显式字体与字号选择。

来源、摘要和许可保存在[字体资源目录](../src/renderer/assets/fonts/noto-sans-sc/SOURCE.md)。OFL 许可加入安装资源，运行时无远程字体请求。构建后 98 个子集作为独立 woff2 文件，其余小子集内联。

### 2. 单一画布与回复按钮

[renderer/index.css](../src/renderer/index.css) 保持 App 为唯一画布所有者，沿淡紫/冰蓝色场提亮底色并增加中央白色柔光，不在侧栏和主列重复叠加灰色遮罩。深色与星光主题保留各自背景。

0.1.237 仅将四个回复操作 SVG 从 17px 缩至 15px，按钮仍为 30px，保留可访问名称、焦点与操作逻辑。

[verify-ui.mjs](../scripts/verify-ui.mjs) 排除 tmp/out/dist/build、文档及 runner 文件的热更新，避免测试产物写入触发夹具刷新。通用浏览器断言同步到最终玻璃表头 caption 色；未为通过断言更改产品配色。

## 五、完整需求导入与模型预算（0.1.238）

### 1. 导入预算与聊天摘录解耦

[document-attachment-service.ts](../src/main/services/document-attachment-service.ts) 的 `requireComplete` 模式不再使用普通聊天的单文件 24,000/总计 80,000 字符摘录预算，完整需求导入上限为 2,000,000 字符。单文件 32 MB、40 文件、ZIP 完整需求拒绝及链接检查继续保留。

新需求与补充材料不再调用旧 48,000 字符门槛。解析正文进入 source 文档存档，空正文与导入超限分别报错；不以静默截断继续需求评测。普通聊天仍采用原摘录预算。旧需求包导入等其他既有边界不属于此次全面解除范围。

### 2. 全段读取与汇总

[requirement-source-reader.ts](../src/main/services/requirement-source-reader.ts) 提供无损切片与逐段整理。分段优先按段落或换行切开，硬切不拆 Unicode 代理对，并保留存档字符区间。每个原文片段都处理成功后才开始必要的递归汇总，不采用只保留开头的降级方式。

[RequirementEngineeringService](../src/main/services/requirement-engineering-service.ts) 按所选模型的上下文、有效输出预算及安全余量计算可用输入。原文工作预算最多取可用输入的约四分之一，并设 96,000 字符工作上限；这用于给代码证据、阶段文档和提示保留空间，不是附件拒收阈值。分段输入最多 24,000 字符，笔记限额与输入大小关联。

分段笔记保存为 `requirement-analysis/source-reading` 中间产物，带源文档 ID、存档路径和字符位置。检查点绑定输入、模型、输入/输出预算、约束及产物 SHA-256，复用前核对本地与工作区文件完整性。

空笔记、超预算、无法收敛、读取异常或取消均停止后续分析，不跳过失败片段。失败且未发布的长需求运行可用空 `/requirement` 重试；新轮次排除旧失败阶段草稿，同时复用有效分段。当前用户决定在摘要外保留，优先于早期材料。

### 3. 每次模型请求预检

[token-estimate.ts](../src/shared/token-estimate.ts) 提取原 ContextManager 的多语言估算，共用于聊天和需求服务，避免新增不同口径。需求首轮和自动续写都预检输入预算，输出预算仍由既有能力档案解析。

这里的预算为保守估算，不是供应商 Tokenizer 的精确计数。中间文档累计过大或能力配置不准确时，后续阶段仍可能明确报上下文不足；原文和阶段产物保留。摘要属于模型派生参考，不证明每条业务规则已无遗漏。

## 六、模拟分支继续执行（0.1.238）

`simulate-materials` 沿用原 typed submit 接口和同一运行，不增加工具执行后门：

```ts
{ conversationId, runId, action: 'simulate-materials' }
```

操作仅接受对应会话下有效的等待材料运行，复用互斥、工作树校验及取消机制，顺序生成以下中间文档：

| 文档维度 | 内容 | 发布属性 |
| --- | --- | --- |
| `modeling/material-preview` | 模拟材料、假设与初步规格预览 | 草稿 |
| `modeling/material-draft-modeling` | EARS 业务需求与 BDD 验收场景 | 草稿 |
| `specification/material-draft-specification` | 实施规格、追溯及待核对事项 | 草稿 |

各步保存可校验检查点。`materialPreviewDocumentId` 与新增可选 `materialDraftDocumentIds` 指向产物；旧的仅预览运行可继续，后续失败不会要求重新输入原始需求。正式材料重新复评时清除旧草稿显示指针。

[RequirementClarificationCard.tsx](../src/renderer/components/chat/RequirementClarificationCard.tsx) 展示推进阶段和可展开草稿；待补材料默认折叠，文案明确原需求已沿用。[MessageList.tsx](../src/renderer/components/chat/MessageList.tsx) 更新进行中提示，沿用原会话刷新与错误保留通道。

该分支不写入真实 source、不清除 `pendingMaterials`，不生成 requirement/modeling/specification 正式回执。正式 DSL 与代码生成仍消费已放行产物。未实现“把模拟假设自动认定为已验收业务事实”的路径。
