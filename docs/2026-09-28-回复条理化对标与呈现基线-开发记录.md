## 一、诉求与本轮范围

诉求原话是：「我主要想要 Eva 的回复可以像 Codex 或者 DeepSeek Harness 或者 Claude Code 那样有条理。」

本轮只做了一件事：**把三家真实在用的呈现规则核实清楚，然后把可核实的那部分落到 Eva 的提示词里，并用测试钉住**。没有做架构改动，没有动渲染层，也没有凭印象写规范。

必须先记录一个过程事实：我第一轮给出了四条建议，出处是印象而不是资料。被用户当场质疑「你是查阅了 codex 和 claude code 的资料了吗」之后才去实查，结果**四条里有两条被证据直接否决**。这条教训本身是本轮最重要的产出之一，写进文档是为了防止以后再按印象改提示词。

## 三、被证据否决的两条建议

这两条**没有落地**，后来者不要按那个方向改：

1. ~~「回复固定按 结论 / 发现 / 验证 / 风险 / 下一步 的小节骨架」~~。Codex 现行提示词明确写着 `Avoid section headings`；Claude Code 写的是「简单问题用散文直接回答，不要标题和分节」。加固定骨架恰好是样板化的来源，方向反了。
2. ~~「禁止在结尾提后续方向」~~。Claude Code 原文是「任务完成后提供后续选项是可以的；动手前征求许可是不行的」。要禁的是**临阵脱逃式的征求许可**，不是收尾的选项。

有一条反而被证实必须保留：Eva 原有提示词里把「findings or changes、verification、risks、next steps」列为默认小节的那句，正是样板段落的成因，本轮删掉了它。

## 四、dsh 的真正启示：条理来自机制，不来自措辞

dsh  shipped 的 persona 只有一行（`packages/bundle/web-app/cordis.patch.yml:19`：`You are a coding agent powered by the {{model}} model.`，base 层 `personaPrefix: ''`）——**它几乎没有回复塑形提示词**。它的「有条理」来自三处机制：

- 过程与正文的分界由 harness 派生：`turn-process.ts:163` 的 `answerAnchorSeq: answer.finalNode.seq`，最终回答之前的节点自动折叠进可展开的过程区。
- 待办清单由 harness 回声：`tool-todo/src/index.ts:46-54`，`Updated todo list: N pending, M in progress, K completed`，并规定 trivial 单步任务跳过待办工具。
- 陈述受会话证据约束：`tool-goal/src/wrapup.ts:6`「只报告此前轮次与工具结果真正确立的内容，会话里没有的细节要直说而不是编」。

另外它有三条工程实践值得抄：提示词由「各插件-owned 的有序分段 + 集中分配的 order」组合而成；模板里未知或空的 `{{var}}` 直接抛错；模型可见文本被 pin 成 `snapshots/**/system-prompt.expected.md`，改文案 CI 就红，且 invariant 是「模型可见 ⟺ 已记录」。

这三条都属于**架构层**，本轮未动，记为第四批候选。

## 五、本轮落地的五项改动

1. **`base` 重写**（`src/main/agent-engine/context.ts:508`），提炼成一句可测的「可读优先」基线：
   - 开头即结论：第一句回答「发生了什么 / 查到了什么」，细节与理由在后，按「最易评估结论」排序而非按时间叙述（对应 Codex 的 `Lead with the outcome` 与 `in the order that makes the conclusion easiest to assess, rather than recounting your work chronologically`）。
   - **可读与简短是两回事，且可读更重要**：缩短靠取舍（删掉不改变读者下一步动作的细节），不靠把文字压成碎片、缩写、`A -> B -> 失败` 这类箭头链或术语；留下来的内容一律写完整句（对应 Claude Code 的同名段落与 `arrow chains like A → B → fails`）。
   - Markdown 是阅读辅助不是模板：标题、列表、表格、引用、代码只在承载真实结构时出现，绝不作装饰；表格只装可枚举的短事实（对应 `a simple question gets a direct answer in prose, not headers and sections. Use tables only for short enumerable facts`）。
   - 一段一个意思、列表前留空行、简单问题用散文回答。
   - 删除原先列举默认小节的那句（见第三节末）。
2. **新增收尾纪律**（`context.ts:428`）：收尾段落若是计划、开放问句、下一步清单或「我接下来会……」式承诺，而现有工具当场就能做完，**必须先做完再交回控制权**；「宣布一步却不在同一步里执行它，会把用户晾在那里」（对应 `Before ending your turn, check your last paragraph` 与 `Announcing a step without the tool call in the same turn hands control back with the work still pending`）。
3. **计划块加门槛**（`context.ts:439`）：只有至少三个彼此独立、用户值得跟踪的步骤才开 `plan`，一两步或琐碎任务直接作答。三家口径一致：Codex「roughly the easiest 25% 不用计划工具」、Claude Code「只有一个琐碎任务时别用这个工具」、dsh「trivial 单步任务跳过」。
4. **即时勾选 + 禁止二次草稿**（`context.ts:440`、`442`）：每条完成当场汇报，不许攒到末尾一次倾倒；**在没有任何 `step` 消费过计划之前不得重发 `plan`**——那不是改版是改口，会当场作废用户正在看的清单并把界面切成「已调整」。这两条直接来自实测到的会话 `e7f7ee14`：一个 4 行计划刚发出，就被同轮另一个 3 行计划顶掉，用户看到的清单瞬间归零重来。
5. **最终汇总提示同步**（`src/main/agent-engine/agent-runner.ts:973`）：在工具跑完后的无工具汇总指令里补上「靠取舍缩短、保留完整句与连贯散文、不要电报体碎片」。这一条容易漏：用户实际读到的那一版是这条指令产出的，只写进系统提示词会被它覆盖。

刻意没做的一件事：没有在 `agent-runner.ts` 的汇总指令里加「用手边工具继续做」的收尾纪律。那条请求是以 `tools=undefined` 发出的，要求模型继续调工具会直接失败——收尾纪律只应存在于系统提示词。

## 六、支撑上述判断的真实回复诊断

抽取本机 userData（`%APPDATA%/eva`，注意较新的会话已无 `messages.json`，数据在 `conversations/<id>/message-pages/*.json`）中的助手行做了统计。发现的缺陷与本轮改动的对应关系：

## 九、使用注意

- 措辞类规则是概率约束，不是硬保证。它提升的是收敛概率，判定要以真机跑同类任务的对比为准。
- 两条「可读优先」的表述必须**同时**存在于 `base`（`context.ts:508`）和最终汇总提示（`agent-runner.ts:973`）。只改一处会退化成旧行为：汇总轮把内容压成碎片。这条已写进 `REGRESSION-GUARDS.md`。
- 计划门槛是「至少三个彼此独立步骤」。两步但每步都不轻的边界，仍由模型自行取舍，不是缺陷。
- 简单问答仍然不生成执行过程、验证、风险、下一步等段落——本轮删的是「默认小节清单」，不是「克制」本身。
