# 存储可靠性与启动兜底修复开发记录

日期：2026-09-10
版本：0.1.205

## 背景

当日对当前工作区的全量审计（架构 / 存储 / 渲染 / 安全）中，存储层有三项被判为 P0（数据丢失风险与启动失败风险）。本文档记录这三项的修复，以及启动失败可见化改造。其余审计条目未动，见文末"遗留事项"。

## 一、会话消息分页：崩溃与索引损坏下的数据丢失（P0）

### 风险

1. 页索引 `message-pages.json`、页文件与元数据此前用 `writeFileSync` 直写，崩溃/掉电会留下截断的 JSON；读取方按"缺失"处理，正好进入重建路径。
2. 索引丢失后按旧 `messages.json` 重建时，新页沿用 `page-${pages.length+1}` 编号，重建出的 `page-000001` 会**覆盖磁盘上同名旧页**，旧消息静默丢失。
3. "空索引 + 磁盘仍有页文件"的中间态（此前部分恢复写入过空索引）会把全部历史孤儿化。

### 修复（conversation-store.ts）

- 新增 `writeJsonAtomic`：唯一临时文件（`.<uuid>.tmp`）+ rename 落盘，索引、页面、元数据全部改走原子写（conversation-store.ts:81）。崩溃只会留下旧版本，不会产生截断 JSON。
- `ensureMessagePages` 的恢复优先级改为"磁盘页 > 旧 messages.json"：索引缺失/损坏时先遍历 `message-pages/` 实际文件重建索引（`recoverPagesFromDisk`，conversation-store.ts:165）；空索引但磁盘有页时同样恢复，不再孤儿化历史。
- 新增 `nextMessagePageId`（conversation-store.ts:187）：页号只增不复用，已存在同名文件的编号会跳过，重建后不可能覆盖磁盘旧页。

### 验证

- 新增用例：`recovers the page index from disk pages instead of a stale legacy transcript`；`never reuses a page id whose file still exists on disk`；以及分页迁移用例（`writes new messages in bounded pages and lazily migrates legacy transcripts`）。
- storage 单测 22 项全部通过。

## 二、AgentStore 读-改-写竞态（P0）

### 风险

`createAgent` / `updateAgent` / `deleteAgent` / `initializeBuiltInAgents` / `alignBuiltInConnections` 的 read→modify→write 之间没有串行化，两个并发保存都读到旧快照时，后写入的更新会覆盖前者（丢失更新）；且所有写操作共用固定的 `agents.json.tmp`，并发时互相踩踏。

### 修复（agent-store.ts）

- 新增 `writeLock` + `enqueue`（agent-store.ts:32），上述五类写操作全部串行化，读-改-写作为整体执行。
- 临时文件名改为 `${filePath}.${uuid}.tmp`，避免并发写共用同一临时文件；rename 失败时清理临时文件再抛出。

### 验证

- 新增用例：`serializes concurrent agent updates so no change is lost`。

## 三、配置损坏导致应用打不开（P0）与启动失败可见化

### 风险

`config.json` 损坏时 electron-store 构造函数抛错（`clearInvalidConfig` 默认 false），而 `initializeStorage()` 没有 try/catch，窗口从未创建——表现为黑屏/闪退，且没有任何提示；存储层是唯一没有被保护起来的启动依赖。

### 修复

- `config-store.ts`：
  - 新增 `openStore()`（config-store.ts:120）：捕获 `SyntaxError` 时先把损坏文件备份为 `config.json.corrupt-<时间戳>.bak`（best-effort），再用 `clearInvalidConfig: true` 重新打开，从默认值继续启动。
  - 新增 `repairInvalidShape()`（config-store.ts:147）：对 `providers` / `fileAccessGrants` / `modelPools` / `costRateCards` / `workspacePath` / `activeProviderId` / `activeModel` / `automation` / `network` / `environmentRules` 做形状校验，只把形状不可用的键重置为默认值，其余有效配置保留。
- `src/main/index.ts`：启动流程改为 `startApplication()` 包 try/catch，失败时打印错误、`dialog.showErrorBox` 弹窗提示原因并以退出码 1 退出，不再静默留下一个没有窗口的进程。

### 验证

- 新增测试文件 `tests/unit/config-store.test.ts`（走真实 electron-store + mock electron，2 个用例）：从默认值启动并备份不可读配置；只修复形状非法的键、保留有效取值。

## 遗留事项（本次未动）

审计其余条目按严重度排队，代码均未修改，摘要如下：

- **P1**：取消（abort）时已生成的部分输出不落盘、进度卡成为孤儿；任务编排的重试门失效且无退避；OpenAI SDK 默认重试与外层重试叠加放大到 12 次；两处 `void start*TaskRun` 未 catch；流式缺少空闲看门狗。
- **P2**：打字机逐字符低效实现与队列残留；两处无 selector 的整树订阅；progressUpdates 无界增长；若干安全边界与既有范式不一致（浏览器弹窗未走外部 URL 策略、IPC 授权根未校验属于已注册工作区、个别工具硬编码绕过 Agent 工具白名单等）。
- **P3**：CI 监听分支与仓库主分支不一致（push 不触发）；无 lint 脚本。

## 使用注意

- 配置自愈只会重置"形状不可用"的键；若配置曾被备份为 `.corrupt-*.bak`，可对照备份手动恢复个别取值。
- 消息分页为惰性迁移：老会话在首次读写时才从 `messages.json` 迁移，迁移前旧文件保持原样，不会被删除。
