# 确定性代码生成（/coding）的生成器插件

> 适用阶段：RMSD 流水线的最后一段。`/coding` 之后不再调用任何模型。
> 代码位置：`src/main/services/codegen/`。

## 1. 为什么要有这一层

在补齐之前，`/coding` 只有一个写死的适配器 `builtin-java-reference`：它能做的只是把每个实体变成一个字段声明类，commands / events / states / rules 全部留在语义包里"待适配"。结果是：

- 想生成别的目标（Maven 工程、SQL、JSON Schema、XCERP 的 MyBatis）必须改流水线本身；
- DSL 里写了 `stage: Workflow` 这样的类型，会被**静默**当成 `String`；
- 验证器只 `stat` 一下文件是否存在，名字对不上就报错，对生成内容没有任何断言。

现在的结构是：`/coding` 只认"注册表里有一个 id 叫 X 的生成器"，具体生成什么由生成器决定。

## 2. 生成器契约

`CodeGenerator`（`codegen/types.ts`）：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定标识，写进 target model、manifest、`generation-result`，也是复用的比对依据 |
| `label` | 进度与报告里的人读文案 |
| `target` | 目标格式（`java` / `sql` / `json-schema`） |
| `outputKind` | `reference`（参考实现，不可当生产交付）或 `production` |
| `capabilities` | 它能覆盖的 DSL 能力名，用于语义包的 `generation_map` |
| `options` | 它认识的选项**及允许值**；未声明的选项直接拒绝 |
| `generate(parsed, context)` | **纯函数**：DSL + 选项 → 文件列表 + manifest。无时钟、无随机、无隐式 I/O |

`generate` 拿到的 `context`：`outputDirectory`、`options`（已校验）、`declaredTypes`（字段名 → 归一化类型）。

纯函数这点是刻意的：同一个 DSL 必须产出同样的字节，否则"确定性"只是口号。测试里有一条 `produces byte-identical output` 守着它。

## 3. 已注册的生成器

| id | target | outputKind | 产出 | 需要后续适配 |
| --- | --- | --- | --- | --- |
| `java-reference` | java | reference | 每实体一个 `Xxx.java`（私字段） | commands / events / states / rules |
| `java-maven` | java | reference | Maven 目录树 + `pom.xml` + 每实体单测 | commands / events / states / rules |
| `json-schema` | json-schema | production | `domain.schema.json`（draft 2020-12） | 无（schema 本身即完整产物） |
| `sql-ddl` | sql | reference | `schema.sql`（PostgreSQL DDL） | migration-approval |

`java-reference` 的字节输出与重构前**完全一致**，所以磁盘上已有的 content-addressed 包仍然通过验证，不会被重算（有专门的回归测试固定这段文本）。

### 类型映射

DSL 先归一化，再交给生成器（`parseFieldType` / `TYPE_ALIASES`）：

```
String/Str/Varchar        -> string      Money/Decimal/Double -> decimal
Text/Content/Memo         -> text        Bool/Boolean         -> boolean
Int/Integer/Number        -> int         Date                 -> date
Long/Bigint               -> long        Timestamp/DateTime   -> datetime
GUID/Uuid                 -> uuid
```

**未知类型 = 报错**，不再退化为 `String`：

```
The DSL type "Workflow" is not one Eva can generate from. Use one of: string, text, int, long, decimal, boolean, date, datetime, uuid. (entity Deal, field stage)
```

各目标的落点：

| 归一化类型 | java | sql | json-schema |
| --- | --- | --- | --- |
| string / text | `String` | `varchar(255)` / `text` | `string` |
| int / long | `int` / `long` | `integer` / `bigint` | `integer` |
| decimal | `java.math.BigDecimal` | `numeric(18, 4)` | `number` |
| boolean | `boolean` | `boolean` | `boolean` |
| date / datetime | `LocalDate` / `OffsetDateTime` | `date` / `timestamptz` | `string` + format |
| uuid | `java.util.UUID` | `uuid` | `string` + format |

## 4. target model：谁批准了这次生成

`/coding` 会把批准过的目标声明写到 `intermediate/runs/<dslHash>/02-generation-ir/target-model.yaml`：

```json
{
  "schema_version": "1.0",
  "target_id": "eva-billing-java-reference",
  "generator": "java-reference",
  "approval_status": "approved-for-non-production-reference-output",
  "production_output": false,
  "output_kind": "reference",
  "options": {},
  "overwrite_policy": "refuse-non-empty-output"
}
```

规则（`readTargetModel`）：

1. 文件不存在 → 用注册表默认（`java-reference`）写入一份。默认值显式写死，不是"取第一个注册的"，所以新注册生成器不会悄悄改变既有 DSL 的产出。
2. 文件存在但不是 JSON → **整轮失败**，不会回落到默认值。
3. `generator` 不存在 → 报错并列出可用 id，绝不回落到默认。
4. `options` 里有未声明的键或非法值 → 报错。
5. `production_output: true` 但生成器是 `reference` → 拒绝。
6. `output_kind` 与生成器自报不一致 → 拒绝。

想换目标，就是把这些字段写对（`generator` 改成 `sql-ddl` 之类）再跑 `/coding`。

## 5. 产物与验证

每个 DSL 的产物在 `coding/output/runs/<dslHash>/03-generated-code/`，其中必有 `generation-result.yaml`：

```json
{
  "schema_version": "1.0",
  "adapter": "sql-ddl",
  "adapter_label": "PostgreSQL DDL adapter",
  "target": "sql",
  "output_kind": "reference",
  "generated": ["sales_orders", "notes"],
  "preserved": ["commands", "events", "states", "rules"],
  "requires_target_adapter": ["migration-approval"],
  "details": { "schema": "public" }
}
```

验证器检查的是：`result` 里的 `adapter` 与本次生成器一致、`generated` 非空、包内除了 result 之外**确实还有文件**。它不把 `generated` 当文件名比对——那些是 DSL 构件名（`Invoice`、`sales_orders`），一个 SQL 文件对应多张表，Java 一实体一文件，这个差别只有生成器知道。

写入策略是**内容寻址 + 拒绝覆盖**：同目录已有不同字节的内容就抛 `Existing deterministic artifact differs`。否则两次不同结果会声称自己是同一份。

## 6. 加一个新生成器

1. 在 `codegen/` 新建文件，实现 `CodeGenerator`。`options` 里只写你真的会读的键，值域写全。
2. 类型映射用 `ParsedDslField['type']`（已归一化），不要把原始拼写再判一遍。
3. 在 `codegen/index.ts` 的 `ensureCodeGeneratorsRegistered` 数组里加一项。
4. 文件路径一律相对输出目录；越界的路径会被 `writeGeneratedPackage` 拒绝（有测试守着）。
5. 单测固定三件事：**同一 DSL 两次输出字节相同**、**verification 通过**、**选项错误被拒**。

不需要改 `requirement-engineering-service.ts`，也不需要动 DSL 解析。

## 7. 已知边界

- **不编译、不跑测试**：验证是结构性的。要真正确认 Java 能编译，需要接 `mvn` / `javac`，那是另一个边界（牵涉 sandbox 与耗时）。
- **SQL 是 reference**：`schema.sql` 是完整 DDL，但执行它是 schema migration，流水线的 `prohibited` 明确禁止，所以标成需要 `migration-approval`。
- **MySQL 方言未覆盖**：`sql-ddl` 产出的是 PostgreSQL 方言（含 `timestamptz`、双引号标识符）。换库要另写生成器，不要把方言差异塞进 option。
- **XCERP / MyBatis 仍无生成器**：仓库里的 `docs/code-production-pipeline架构说明.md` 记录的是外部 Python 流水线，尚未移植过来。
- **`generated` 是构件名不是文件名**，前端如果要展示"生成了哪些文件"，应该读目录而不是读这个字段。
