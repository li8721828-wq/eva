# Eva 需求到代码流水线

自 0.1.240 起，修改现有项目功能优先使用需求卡的“实现现有项目功能”：所选运行时的 Agent 在独立工作树读取现有代码、修改并执行检查，不要求先生成 DSL。本文介绍的确定性生成保留为“生成独立领域模块（可选）”。实施会话返回后须审查实际差异与测试记录，业务验收仍待确认。详见[业务实现流程改造方案](2026-11-27-业务实现流程改造方案.md)。

## 从需求生成领域模块

1. 在项目会话用 `/requirement` 提交需求与附件，完成业务澄清。
2. 用 `/requirement-modeling` 生成建模结果，再用 `/spec` 生成最终实施规格草稿。通过质量检查后，在对话中确认关键规则与例外，Eva 发布这版 Spec 与验收契约。
3. 用 `/dsl java-domain` 生成 Java 目标的领域 DSL。Eva 在发布前核对契约中的守卫、角色、状态和事件字段，再做语义审查。通用参考目标可使用 `/dsl`。
4. 用 `/coding` 按所选目标生成 Java 17 Maven 模块。Eva 校验逐文件摘要，使用本机 JDK 编译并运行领域行为测试与独立 Spec 验收，通过后才标记完成。

在同一需求运行中操作。可以在同一工作树的另一会话继续，进度和待确认卡片会跟随发起命令的会话。修改上游内容后，从对应阶段重新执行，重新验证下游。原工作区产物与发布摘要不一致时会阻断。Java 生产目标使用第 4 版独立验收契约，旧版产物可作为历史参考。用旧 Spec 生成或验收 Java 生产模块前，重新运行 `/spec`、确认规则，再运行 `/dsl java-domain` 和 `/coding`。

需求澄清卡用于确认业务决定。仍需清单、权限矩阵或样本时，Eva 会停在「等待补充验收材料」。在原会话发送 `/requirement` 并添加附件，或把材料正文写在命令后，Eva 会在同一运行继续复核。已确认事项只有在后续材料提供可核对的冲突证据后才重新打开。显示「需求评测需要复核」时，可以单独发送 `/requirement` 重试。

`/coding` 使用当前 DSL 的已批准目标。首次未指定目标时使用 `java-reference`。输入 `/coding <生成器 ID>` 可以切换目标。需要选项时，可编辑该 DSL 的 `coding/intermediate/runs/<DSL SHA-256>/02-generation-ir/target-model.yaml`（JSON 格式），再用 `/coding` 执行。Java 目标需要 PATH 中的 JDK 17 或更新版本。

## 缺少真实材料时继续模拟试验

模拟材料生成的建模与规格草稿可以沿用，不必重新输入需求。自 0.1.239 起，草稿卡会显示实际的规格、DSL 或代码阶段；正式材料是否齐全独立显示。

点击“采用当前模拟假设，继续生成 DSL 与试验代码”，Eva 会以现有草稿生成带追溯编号的试验规格交接稿，生成并核对 DSL，再在同一需求目录的 `trial/` 分支生成参考代码。也可在原会话依次执行 `/spec`、`/dsl`、`/coding`。`/coding` 只消费已有试验 DSL，不调用模型；没有 DSL 时会提示先执行 `/dsl`。

试验默认使用 `java-reference`，也可选择 `/dsl java-maven` 或 `/dsl sql-ddl` 等参考生成器。Java 参考产物会进行真实 JDK 编译；文件清单和摘要会校验，尚未实现的命令、状态、规则等目标适配会单独列出。生成参考文件不代表完整业务模块已实现或正式验收通过。

试验产物与假设说明保存在 `trial/<输入摘要>/<DSL 摘要>/<生成器>/` 下，不覆盖项目应用源码，不生成正式发布回执。`java-domain` 等生产目标仍需要正式 Spec 与验收契约。补充真实材料后用 `/requirement` 复核，旧试验入口失效，但历史试验文件保留。

失败或取消可从原卡片继续；已完成交接稿和 DSL 按摘要复用。上游文件被改动时停止，要求更新草稿；参考代码文件被修改时也不会静默覆盖。

## 目标与产物

| 生成器 | 产物 | 发布前验证 |
|---|---|---|
| `java-domain` | Java 17 Maven 模块，含实体、命令、状态、角色检查、守卫规则、事件及行为测试 | 逐文件摘要、JDK 编译和领域行为测试 |
| `java-reference` | 实体字段的 Java 参考实现 | 逐文件摘要及 JDK 编译 |
| `java-maven` | Maven 布局的 Java 参考模块，支持 `useRecords` 和 `nativeTypes` | 逐文件摘要及主源文件编译 |
| `json-schema` | JSON Schema 2020-12 实体结构 | 文件清单与摘要。DSL 含领域行为时，生产模式需要相应适配 |
| `sql-ddl` | PostgreSQL DDL 参考脚本 | 文件清单、摘要及生成时的表列命名检查。迁移需单独审核 |

Java 领域模块由调用方传入实体、当前状态和已认证角色。命令执行后返回新状态和事件，应用负责持久化、鉴权上下文、事务和事件分发。领域模块可复制到业务仓库后用 `mvn test` 测试。Eva 中的输出目录作为已校验的原始产物保留，Maven 构建输出应放在工作副本中。

## 宿主 Maven 集成验收

在宿主 Git 仓库根目录对应的项目会话中操作。先在当前需求运行的 `coding/host-target.json` 保存完整提交 SHA、Maven 模块相对路径和宿主测试类全名。根模块使用 `.`。例如以下配置中的提交 SHA 应替换为 `git rev-parse HEAD` 的实际值。

```json
{
  "commit": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "module": "approval-service",
  "tests": ["pilot.ApprovalHandlerTest"],
  "adapterPatch": true
}
```

`adapterPatch` 为 `true` 时，在同一目录提供 `host-adapter.patch`。它以固定提交为基线，包含目标模块的 Java 业务接入与测试差异。Eva 会把已验收领域模块的 Java 源码和测试叠加到同一模块，补丁范围限于该模块的 `src/main/java` 和 `src/test/java`。`tests` 至少选择一个经宿主业务入口实际调用生成工作流的测试类。

1. 可先执行 `/verify-host preflight`。Eva 核对 Maven、JDK 17+、固定提交和模块，在隔离副本离线运行原始提交的 `test-compile`，并报告缺失的本地依赖。
2. `/coding java-domain` 通过后执行 `/verify-host`。在需求工作区打开「查看宿主补丁」，审阅新增与修改的文件。补丁保留 Git 生成的原始字节，保存到 `coding/output/host/<补丁 SHA-256>.patch`。
3. 执行 `/verify-host run`。Eva 复核摘要，在独立副本预检后，用干净的 Git 副本应用预览的同一份补丁并运行 Maven `verify`。指定的宿主测试和生成模块验收测试都须有本次 Surefire 通过报告。Eva 还会在一次性对照副本中验证宿主测试确实经业务代码到达生成工作流。结果写到 `coding/output/host/verification.json`，记录提供调用证据的测试类。

构建使用 PATH 中的 Maven 和本地依赖仓库。宿主环境需预先提供构建依赖。验证针对固定提交及预览差异，实际交付可以在审阅后使用导出的补丁。

## Java 领域 DSL

下面的订单示例演示最小工作流。每个 `trace` 必须引用当前已发布规格中的真实编号。

```text
domain Sales
version 1
entity Order {
  id: uuid
  total: decimal
  trace: FR-001
}
state Pending {
  entity: Order
  initial: true
  trace: FR-001
}
state Approved {
  entity: Order
  trace: FR-001
}
event OrderApproved {
  entity: Order
  fields: id, total
  trace: AC-001
}
rule PositiveTotal: Order.total > 0 [trace: FR-001]
command Approve {
  entity: Order
  actor: Finance
  from: Pending
  to: Approved
  emit: OrderApproved
  requires: PositiveTotal
  example: {"total":"125.00"}
  trace: FR-001
}
```

- 工作流的状态、事件、规则与命令必须属于同一实体，每个工作流恰有一个初始状态，所有状态都须可达。
- 命令声明角色、源状态、目标状态和一个事件。无载荷事件可以省略 `fields` 或使用 `fields: []`。守卫支持 `int`、`long`、`decimal` 的比较和布尔等值比较。多个 `requires` 用逗号分隔，按声明顺序检查。
- 有守卫的命令必须提供覆盖守卫字段的合成正例。数值用 JSON 字符串保证精度，布尔值可用 `true` 或 `false`。无守卫的命令可省略 `requires` 和 `example`。
- 遇到 `OPEN:`、未知字段、未映射行为或不可执行的正例时阻断相应阶段。跨实体事务、外部集成、数据库和框架接入需要独立适配。

## 从 Spec 固定验收结果

`/spec` 同时发布 `implementation-specification.md` 与 `acceptance-contract.json`。每个 FR 有唯一记录，包含触发条件、预期结果和 AT 验收编号。用例在 DSL 生成前固定，声明实体、命令、起始状态、角色和输入。每个 Java 领域命令至少有一个成功用例和一个拒绝用例。成功用例的 `expect` 声明目标状态、事件类型和 `payload` 的完整字段及预期值。无字段事件使用空对象。拒绝用例声明角色、状态或具体守卫。

关键规则在最终 Spec 中逐条分配 `BR` 编号。验收契约的 `checks` 必须匹配同一 `BR` 的编号、FR 归属、类型和可执行条件。确认卡会显示具体的角色、命令起始状态、工作流初始状态，以及守卫字段、比较符和阈值。角色、命令起始状态和布尔守卫要求配对拒绝用例，除目标条件外使用相同输入。每个数值守卫覆盖可表达的低于、等于和高于阈值。被较早条件拒绝的用例不能计入后续覆盖。数值在 JSON 中用字符串保存。

```text
- BR-001 [FR-001] [numeric] `Order.Approve.MinimumTotal total >= 100000`
- BR-002 [FR-001] [actor] `Order.Approve actor = Finance`
- BR-003 [FR-001] [state] `Order.Approve from = Pending`
- BR-004 [FR-001] [initial-state] `Order initial = Pending`
```

选择 `java-domain` 时，`/dsl` 就会阻断缺少双签守卫、把 `>=` 改成 `>`、初始状态不符或遗漏事件金额字段等结构错误。`/coding` 继续执行同一校验，真实 JDK 验收测试核对契约指定的初始状态、实际状态迁移、拒绝路径和事件字段值。

DSL 必须把用例命令追溯到对应 FR。外部集成等暂时无法自动执行的验收，可以在契约用 `manual` 说明所需证据，且保留空 `cases`。这些规则可继续供审阅和参考生成，`java-domain` 会列出缺少可执行验收的 FR 并停止发布。

## 恢复与变更影响

需求分析和规格构建检索当前工作树。索引用于定位候选文件，证据引用实际读到的相对路径、行号和文件 SHA-256。扫描与摘录有上限，缺少相关片段时标为实现前待核对。

需求审计的 `READINESS`、未决事项和 `BLOCKERS` 必须一致。需求到 DSL 的首轮和续写请求使用当前模型连接的输出预算，受已知上游上限和上下文约束。

Spec 中断可重试 `/spec`，DSL 中断可重试 `/dsl`。恢复会复用本次尝试中输入、模型选择和文件摘要仍一致的检查点。重新发布、修改上游或检查点受损时，受影响内容会重新生成。最终放行审查每次重新运行。

代码清单的 `impact` 对比同一需求运行、同一目标的上次成功产物，列出受影响的 FR、关联命令、变更用例及新增、修改、移除的文件。每次 Java 发布仍运行完整模块编译和验收。首次发布建立基线。

## 文件完整性和历史产物

已发布阶段绑定上游文档与自身 SHA-256。模型生成的草稿保留在需求记录中，下一阶段只消费通过放行的文档。

生成目录是 `coding/output/runs/<生成键>/03-generated-code/`。生成键包含代码生成契约版本、DSL、Spec 与验收契约的 SHA-256、规范化后的目标和选项。目标发生变化时会写入独立目录。每次执行都核对 `generation-result.yaml` 中的清单及摘要，缺失的确定性文件可以重建，已有不同内容会阻断并保留现场。发布状态和目标验证记录在同级的 `codegen-manifest.json`。

`/coding` 全程由本地注册的生成器与工具执行，模型调用为零。Java 模块的验收测试覆盖声明的状态迁移、事件及字段、角色或状态拒绝与缺少守卫输入。模型参与的需求、规格和 DSL 审查仍需项目真实需求验收。
