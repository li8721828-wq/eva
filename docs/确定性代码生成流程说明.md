# Eva 需求到代码流水线

## 从需求生成领域模块

1. 在项目会话用 `/requirement` 提交需求与附件，完成业务澄清。
2. 用 `/requirement-modeling` 生成建模结果，再用 `/spec` 生成最终实施规格。规格必须达到质量阈值、清空阻塞项，并通过最终正文与独立验收契约的复核。
3. 用 `/dsl` 生成领域 DSL。发布前检查语法、规格编号及领域行为的覆盖。
4. 用 `/coding java-domain` 生成 Java 17 Maven 模块。Eva 校验逐文件摘要，使用本机 JDK 编译并运行领域行为测试与独立 Spec 验收，通过后才标记完成。

在同一需求运行中操作。修改上游内容后，从对应阶段重新执行，重新验证下游。原工作区产物与发布摘要不一致时会阻断，历史产物可以作为参考。0.1.211 生成的历史发布仍可读取。要为它们启用独立验收，重新执行 `/spec → /dsl → /coding java-domain`。

`/coding` 使用当前 DSL 的已批准目标。首次未指定目标时使用 `java-reference`。输入 `/coding <生成器 ID>` 可以切换目标。需要选项时，可编辑该 DSL 的 `coding/intermediate/runs/<DSL SHA-256>/02-generation-ir/target-model.yaml`（JSON 格式），再用 `/coding` 执行。Java 目标需要 PATH 中的 JDK 17 或更新版本。

## 目标与产物

| 生成器 | 产物 | 发布前验证 |
|---|---|---|
| `java-domain` | Java 17 Maven 模块，含实体、命令、状态、角色检查、守卫规则、事件及行为测试 | 逐文件摘要、JDK 编译和领域行为测试 |
| `java-reference` | 实体字段的 Java 参考实现 | 逐文件摘要及 JDK 编译 |
| `java-maven` | Maven 布局的 Java 参考模块，支持 `useRecords` 和 `nativeTypes` | 逐文件摘要及主源文件编译 |
| `json-schema` | JSON Schema 2020-12 实体结构 | 文件清单与摘要。DSL 含领域行为时，生产模式需要相应适配 |
| `sql-ddl` | PostgreSQL DDL 参考脚本 | 文件清单、摘要及生成时的表列命名检查。迁移需单独审核 |

Java 领域模块由调用方传入实体、当前状态和已认证角色。命令执行后返回新状态和事件，应用负责持久化、鉴权上下文、事务和事件分发。领域模块可复制到业务仓库后用 `mvn test` 测试。Eva 中的输出目录作为已校验的原始产物保留，Maven 构建输出应放在工作副本中。

## Java 领域 DSL

下面的订单示例演示最小工作流。每个 `trace` 必须引用当前已发布规格中的真实编号。

```text
domain Sales
version 1
entity Order {
  id: uuid
  total: decimal
  trace: FR-001
}
state Pending {
  entity: Order
  initial: true
  trace: FR-001
}
state Approved {
  entity: Order
  trace: FR-001
}
event OrderApproved {
  entity: Order
  fields: id, total
  trace: AC-001
}
rule PositiveTotal: Order.total > 0 [trace: FR-001]
command Approve {
  entity: Order
  actor: Finance
  from: Pending
  to: Approved
  emit: OrderApproved
  requires: PositiveTotal
  example: {"total":"125.00"}
  trace: FR-001
}
```

- 工作流的状态、事件、规则与命令必须属于同一实体，每个工作流恰有一个初始状态，所有状态都须可达。
- 命令声明角色、源状态、目标状态和一个事件。守卫支持 `int`、`long`、`decimal` 的比较和布尔等值比较。多个 `requires` 用逗号分隔，按声明顺序检查。
- 有守卫的命令必须提供覆盖守卫字段的合成正例。数值用 JSON 字符串保证精度，布尔值可用 `true` 或 `false`。无守卫的命令可省略 `requires` 和 `example`。
- 遇到 `OPEN:`、未知字段、未映射行为或不可执行的正例时阻断相应阶段。跨实体事务、外部集成、数据库和框架接入需要独立适配。

## 从 Spec 固定验收结果

`/spec` 同时发布 `implementation-specification.md` 与 `acceptance-contract.json`。每个 FR 有唯一记录，包含触发条件、预期结果和 AT 验收编号。用例在 DSL 生成前固定，声明实体、命令、起始状态、角色、输入和预期状态与事件，或者声明精确的拒绝原因。

金额等数值在 JSON 中用字符串保存。审批联测包含低于、等于、高于 10 万元及缺少双签四个用例。将 DSL 守卫从 `>=` 改成 `>` 后，正好 10 万元的 `AT-002` 会阻断代码发布，即使 DSL 自带的正例通过。

DSL 必须把用例命令追溯到对应 FR。外部集成等暂时无法自动执行的验收，可以在契约用 `manual` 说明所需证据，且保留空 `cases`。这些规则可继续供审阅和参考生成，`java-domain` 会列出缺少可执行验收的 FR 并停止发布。

## 恢复与变更影响

Spec 中断可重试 `/spec`，DSL 中断可重试 `/dsl`。恢复会复用本次尝试中输入、模型选择和文件摘要仍一致的检查点。重新发布、修改上游或检查点受损时，受影响内容会重新生成。最终放行审查每次重新运行。

代码清单的 `impact` 对比同一需求运行、同一目标的上次成功产物，列出受影响的 FR、关联命令、变更用例及新增、修改、移除的文件。每次 Java 发布仍运行完整模块编译和验收。首次发布建立基线。

## 文件完整性和历史产物

已发布阶段绑定上游文档与自身 SHA-256。模型生成的草稿保留在需求记录中，下一阶段只消费通过放行的文档。

生成目录是 `coding/output/runs/<生成键>/03-generated-code/`。生成键包含代码生成契约版本、DSL、Spec 与验收契约的 SHA-256、规范化后的目标和选项。目标发生变化时会写入独立目录。每次执行都核对 `generation-result.yaml` 中的清单及摘要，缺失的确定性文件可以重建，已有不同内容会阻断并保留现场。发布状态和目标验证记录在同级的 `codegen-manifest.json`。

`/coding` 全程由本地注册的生成器与工具执行，模型调用为零。Java 模块的验收测试覆盖声明的状态迁移、事件及字段、角色或状态拒绝与缺少守卫输入。模型参与的需求、规格和 DSL 审查仍需项目真实需求验收。
