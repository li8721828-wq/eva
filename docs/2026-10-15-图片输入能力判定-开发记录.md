## 一、动因与两层诊断

他的原话：「这样硬编码不好吧，不是应该这个模型可以识别图片就识别吗，而不是根据一份硬编码的文件来判断他能不能识别图片」。背景是他给 deepseek 连接传图被拒。诊断出两层，**都与模型实际能力无关**：

1. **判据是两份拷贝的 OpenAI 名字白名单**（旧 `conversation.ts:258`、旧 `agent-runner.ts:1822`），要求 `provider.type` 为 openai/anthropic；他那条连接 `deepseek123` 的 type 是 `deepseek` → 判据恒 false。
2. **唯一兜底走不通**：`analyzeImagesWithAuthorizedPool` 遍历 `agent.modelPoolIds`，他四个 agent（Coding Assistant / Code Reviewer / Research Analyst / Team Leader）实测全是 `[]` → 候选为空 → 抛旧 `:285` 的英文错，请求在进入模型前中止，转录里也搜不到这句（未落盘）。

同仓其实早有单一真源：`providerRegistry.getModelCapabilities()`（`providers/index.ts:117-123`）+ `inferModelCapabilities` 的 `declared?.supportsVision ?? VISION_PATTERN`——`deepseek-v4-flash-vision-exp` 在那份档案里**已经是 true**，只是聊天链路从不读它。

## 二、判据统一：一个 `supportsImageInput(profile)` 管两头

- 新导出 `supportsImageInput(profile)`（`src/shared/model-capabilities.ts:67`）：`anthropic` 家族直接为真，其余一律 `profile.supportsVision === true`。**声明/探测值优先，模型名只作预填**——`inferModelCapabilities` 里 `declared?.supportsVision` 一旦存在就压倒 `VISION_PATTERN`。
- 聊天发图：`conversation.ts` 的 `primaryModelSupportsVision`（`:265`）改读 `providerRegistry.getModelCapabilities()`；调用点 `:868`（决定是否走视觉池代看）与 `:1344-1345`（剥历史图）。
- runner 侧：`agent-runner.ts` **删除**私有方法 `supportsVisionInput()` 及其模型名正则；`:398` 由 `supportsImageInput(modelCapabilities)` 派生一个 `primarySupportsVision`，原先 5 处调用共用这一个布尔——三处 `ToolContext.supportsVisionInput`（`:685`/`:781`/`:1049`）、浏览器截图注入（`:869`）、历史剥图（`:402`/`:405`）。
- 由此聊天发图与浏览器截图**物理上不可能再给出相反结论**（同一个 profile 来源）。
- `anthropic` 家族豁免是刻意的：`VISION_PATTERN` 认不出他在用的 `claude-opus-4-6-thinking`，不给豁免会打断 Claude 连接。
- 拒绝文案改中文并只写真实可操作路径（`conversation.ts:297`）：「主模型 {model} 这条连接未确认支持图片输入，且该智能体没有可用的视觉模型池。请在 智能体 > 模型访问 里为该智能体挂一个包含 Vision 或 Image 路由的模型池，或改用支持图片的主模型。」——**没提**「在设置里标为支持图片」，因为那个 UI 还不存在。

## 三、一手外部事实（deepseek 谱系，外部文档取证非推测）

- 官方公开模型列表：`deepseek-v4-flash` / `deepseek-v4-pro` / `deepseek-v4-flash-vision-exp`。
- OpenRouter 逐款模态表：V4 Flash 0731 与 0423 的图像输入为**否**；`deepseek-v4-flash-vision-exp` 为**是**（2026-08-21 发布、标实验性、每张图最多按 384 输入 token 计费、文本能力与 V4-Flash 持平）。
