# 瞬态状态行不入最终转录：轮次落定后不再留下「正在……」的行

- 日期：2026-10-13
- 版本/状态：**已提交并推送**。`eva@0.1.206`，分支 `develop`，commit `f5273d1`（17:36:46）。实现与规则确立记录在 `docs/project-memory/CHANGELOG.md` 的 2026-10-12 条目，今日随收口一并入库。所有数字为本文档撰写时重跑所得。
- 主题范围：执行过程可见性——生命周期状态备注（「正在汇总已验证的结果。」这类）的存活边界
- 同日另一条线（界面浮起语言与权限控件）见 `docs/2026-10-13-界面浮起语言收口与权限控件-开发记录.md`

## 一、现象与风险

一轮回复已经落定之后，气泡的过程区里仍留着一行带转圈图标的「正在汇总已验证的结果。」，并且**永远转下去**。

这不只是观感问题：过程区是他要求「执行过程实时可见」时建的，其中的行会被读作执行证据。一条描述进行中的句子在轮次结束后还留在转录里，等于让界面宣称「还有工作在跑」——与仓库规则「不得把模拟的模型推理伪装成真实执行证据」同向冲突。他 10-12 的原话是「这个进展已经结束了，但是还在转圈」，随后要求「把瞬态状态行从最终转录里删掉」。

## 二、根因

状态行同时活在两条通道里，而两条都没有「轮次已落定」这个概念：

1. **落盘通道**：主进程把每条公开状态备注 `push` 进 `executionTimeline` 并随 assistant 消息一起写进转录；渲染层 `ExecutionFeedView` 只按 `kind !== 'reasoning'` 过滤，note 照渲染。
2. **图标判定**：`ProcessReportRow` 里 `entry.kind === 'thinking'` 无条件渲染 `Loader2 animate-spin`，与「这一轮是否还在流」无关。
3. **app-server（ACP/远程）路径更重**：`emitProgress` 每收到一条备注就 `addMessage` 成一条独立的 `progressKind` 消息行，若本轮之后没有后续回复，它会单独成一条消息留在历史里。
4. **store 的 `done` 兜底**：主进程未落盘时由 `use-chat-store` 复制一份 assistant 消息，同样会把 timeline 原样写进去——修了①不修④，状态行仍会从这条路径进历史。

## 三、修复：一条规则，四个落点

规则：**生命周期备注是瞬态信号，只经流事件推送，不进最终转录。**

| # | 位置 | 改动 |
|---|---|---|
| 1 | `src/main/ipc/conversation.ts` | 落盘前 `const transcriptTimeline = executionTimeline.filter((entry) => entry.kind !== 'note')`，写入消息的是它。流事件 `emitExecutionTimeline()` 仍发完整数组，所以**轮次进行期间逐条照旧可见**。 |
| 2 | `src/renderer/stores/use-chat-store.ts` | `done` 兜底分支同样过滤，避免这条路径成为漏口。 |
| 3 | `src/main/services/app-server/server.ts` | `emitProgress` 增 `{ transient?: boolean }`。transient 的行**只 `hub.broadcast`**，既不累积进 `progressUpdates`，也不再 `addMessage` 成独立消息行。ACP 侧的映射备注按 transient 调用。 |
| 4 | `src/renderer/components/chat/MessageBubble.tsx` | 转圈图标改为 `entry.kind === 'thinking' && streaming`；`ExecutionFeedView` 的 timeline 过滤加一层 `streaming \|\| entry.kind !== 'note'`。因此**改动前已落盘的历史会话**也不再显示这些行，且 `hasTimeline` 随之为假，不会留下空的 `.execution-feed` 容器。 |

顺带收窄了公开白名单：`toPublicExecutionNote(content, hasCompletedTool)` → `toPublicExecutionNote(content)`，删掉 `'Preparing the response and any required tools...'` 的映射。理由写进注释：任何工具都没跑过时，这句「正在判断是否需要调用工具」会作为唯一一行留在已完成的回复上方，说的是「什么都没发生」；有工具时它又与后面的判断行重复。

**不受影响的**：工具行、计划/步骤汇报（`progressUpdates` 的正常条目）、真实正文。

## 七、验证缺口

- **未跑真实轮次做端到端确认**。本轮验证到的是：单测覆盖了两条落盘路径的过滤、渲染层过滤条件与图标判定已按 `streaming` 分支、产物含该代码。没有验证的是：一次真实的「有工具调用 → 汇总 → 落定」过程在界面上从「状态行逐条出现」到「落定后只剩工具行」的完整观感。要做这一步需要在他正在运行的应用里发一轮请求（消耗模型配额、产生会话数据），未擅自执行。
- ACP/远程路径的 `transient` 只做了静态与单测层面的确认，未与真实 ACP 客户端联调。

## 八、使用注意与遗留

1. **历史数据不迁移**。改动前落盘的 `executionTimeline` 里仍含状态行，靠渲染层第 4 个落点丢弃；直接读 JSON 做分析时仍会看到它们。
2. **协议修复备注同属 `kind: 'note'`**，因此「检测到未执行的工具调用格式，正在按标准工具协议重试一次」「最终回复达到长度上限，正在续写未完成部分」这类**有信息量**的行现在也只在流式期间可见，落定后从转录消失。如果他认为这类需要留在历史里，得给它们单独的 kind，而不是把过滤放宽。
3. 手机端/ACP 的 `turn/progress` 少了一条前置阶段通知（白名单收窄所致），等待期由客户端自身的流式状态呈现兜底。
4. 过程区文案与形态的既有标准不变：中文分步汇报、与正文同字号、工具行次要、原始思考深藏。
