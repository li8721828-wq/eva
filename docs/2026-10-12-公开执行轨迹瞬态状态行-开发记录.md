# 公开执行轨迹：瞬态状态行不再进入最终转录

- 日期：2026-10-12
- 版本/状态：改动已完成并通过测试，**尚未提交**（HEAD 仍为 `484d10f`，2026-10-09）
- 主题范围：桌面聊天与 ACP 远端两条链路的「过程区状态行」——白名单映射、落盘策略、渲染门控
- 触发来源：用户当日 3 次截图反馈（09:33 / 09:45 / 09:49），指向同一类问题

## 一、变更范围与背景

Eva 的回复气泡上方有一条「执行过程」区，内容由 `AgentRunner` 的生命周期事件经白名单函数 `toPublicExecutionNote()` 映射成中文备注（`src/main/ipc/public-execution-trace.ts`）。当日反馈的三个现象本质是同一件事：**回复已经落定，过程区仍在用进行时宣称「还有工作在继续」**。

三次反馈分别对应三个层次的修复，按时间顺序：

1. 纯问答（无工具）轮次里，过程区只剩一句「正在判断是否需要调用工具。」
2. 有工具的轮次里，已结束的「进展」行图标仍在转圈。
3. 同一轮次里还挂着「已收到工具结果，正在判断下一步。」「正在汇总已验证的结果。」两行状态句，且已被持久化进会话历史。

第三次反馈后确立了一条通用规则，取代逐条删映射的做法：**生命周期备注是瞬态信号，只经流事件推送，不进最终转录。**

## 二、第一项：白名单不再映射首次模型调用标记

**现象。** 一句招呼的回复（正文「嗨。又见面了。」）上方残留灰色小字「正在判断是否需要调用工具。」，用户判定为「没必要显示，很多余」。

**根因。** `src/main/agent-engine/agent-runner.ts:481` 在 `iteration === 0` 时发出生命周期标记 `Preparing the response and any required tools...`，白名单把它映射成该备注。而无工具的轮次在 `agent-runner.ts:631` 就 `yield done` 并 `return`，根本走不到 `Reviewing whether the request is complete...`（`:921`）与 `Synthesizing the available results...`（`:995`），所以这行是纯问答过程区的**唯一**内容——回复落定后仍以进行时宣称在判断，而事实上什么都没在判断。

**修复。** 删除该标记的映射分支，`toPublicExecutionNote()` 对未知标记返回 `null`（`public-execution-trace.ts:12`）。该分支是 `hasCompletedTool` 参数的唯一消费者，且在桌面链路上它的 `true` 分支不可能触发（`iteration > 0` 时 runner 发的是 `Reviewing the tool results...`，已由下一分支映射），因此把参数从签名中移除，两处调用同步改为单参：`conversation.ts:1345`、`server.ts:403`。

等待期的可见性不依赖该备注：`MessageBubble.tsx:717` 一带在 `isStreaming && !message.content` 时渲染 `ExecutionStatusIndicator`（「正在执行…」轮换文案），因此不会退回「加载半天不说话」。

## 三、第二项：已结束轮次的「进展」行不再转圈

**现象。** 一轮已完成的回复（工具行全部绿色对勾、正文路径已渲染成 `FilePathChip`）上方，「进展」行仍带旋转图标。

**根因。** `ProcessReportRow` 的旧版自由格式分支对 `kind === 'thinking'` **硬编码** `<Loader2 className="animate-spin" />`，完全不看 `streaming`。该行内容是工具周期前被 `publishProgress('thinking', …)` 提升的临时正文，轮次落定后就成了「还在干活」的假证据，违反既有护栏「旋转的 active 图标只能出现在流式中的轮次」。同目录的 `PlanChecklist.tsx:29` 早已用 `streaming ? … : undefined` 正确门控，本行是漏改。

**修复。** `MessageBubble.tsx:335` 的图标选择改为 `entry.kind === 'thinking' && streaming` 才用 `Loader2`，否则与 `finding`/`action` 一样落到静态 `CircleDot`（`issue` 仍为 `XCircle`）。`streaming` 由 `MessageBubble` 的 `isStreaming` 经 `ExecutionFeedView → ProcessReportsView → ProcessReportRow` 传入，链路本就存在，未新增状态。

## 四、第三项：生命周期备注只活在流式期间

**现象。** 回复已落定，过程区仍挂两行进行时状态句，且刷新后仍在——说明它们被写进了会话转录。

**根因。** 这些备注由 `toPublicExecutionNote()` 从生命周期标记映射而来，本身不是执行证据（护栏早已写明），却和工具行一起持久化进 `executionTimeline`；ACP 侧还会把每条备注单独 `addMessage` 成一行。落定后它们成为「还在干活」的假状态。

**修复。** 四个落点，缺一不可：

| 落点 | 位置 | 作用 |
|---|---|---|
| ① 主进程落盘 | `conversation.ts:1489` `executionTimeline.filter(e => e.kind !== 'note')` | 最终转录只留工具证据；流事件 `emitExecutionTimeline()` 仍发完整数组，所以轮次进行期间逐条可见 |
| ② 渲染端兜底落盘 | `use-chat-store.ts:897` 同样过滤 | 主进程未落盘的那条路径（`done` 兜底）不把状态行写进历史 |
| ③ ACP 侧 | `server.ts:341/353/406`，`emitProgress` 新增 `{ transient: true }` | 映射备注只 `hub.broadcast`，既不累积进 `progressUpdates`，也不再写独立 `progressKind` 消息行（`collapseToolHistoryMessages` 会把它并进气泡，本轮无后续回复时还会单独成一条消息） |
| ④ 渲染门控 | `MessageBubble.tsx:404` `.filter(e => streaming \|\| e.kind !== 'note')` | **改动前已落盘的历史会话**也不再显示这些行；`hasTimeline` 随之为假，不留空的 `.execution-feed` 容器 |

工具行、计划/步骤汇报与真实正文均不受影响。

## 七、使用注意与遗留事项

1. **主进程改动需重启才生效。** ①③ 位于主进程，`out/main/index.js` 要重建；②④ 是渲染层，可经 HMR 生效。因此真机复核必须重启 dev 实例（`npm run dev:debug`）后再看，本次**未**在运行中的 Eva 内实测。
2. **改动只对新轮次生效，不迁移历史数据。** 历史会话已落盘的 `executionTimeline` 仍含状态行，靠第 ④ 点的渲染侧过滤屏蔽显示；数据本身不动。
3. **协议修复备注同为 `kind: 'note'`**（「检测到回复包含未执行的协议标记，已自动重组并重试。」），按新规则一并从落盘与已结束视图中剔除。它在流式期间仍可见；若将来需要作为可追溯证据保留，应给它独立于生命周期备注的类别，而不是按文案关键词豁免。
4. **手机端 ACP 客户端**若在本地自行持久化 `turn/progress` 的 thinking 通知，其历史仍会含状态行——那属客户端侧行为，本次未改通知内容。
5. 渲染侧的 note 过滤与图标门控**没有自动化测试覆盖**（仓库无 jsdom / @testing-library，判定写在组件内联），依赖代码审查与目检。
