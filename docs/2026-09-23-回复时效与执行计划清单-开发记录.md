## 一、逐字排空改为按积压自适应，字级动画只留一层

**现象**：几千字的回复要几分钟才吐完，`done` 排在队尾等它；同时字符还在被动画两次，观感既慢又抖。

**根因**：逐字队列每个 tick 固定放一个字符（`CHARACTER_INTERVAL_MS = 42`），与积压量无关；而 Streamdown 自身另带一层按 token 的淡入（`animated={{...}}`），两层字级动画叠加。

**修复**：

- 队列从 `use-streaming.ts` 的内联实现抽成独立模块 `src/renderer/lib/stream-reveal-queue.ts`，按会话隔离，可注入 sink 与放行判据（`:56` `setRevealSink`、`:60` `setRevealPacingCheck`）。
- 节奏改为 backlog-aware：`src/renderer/lib/stream-reveal-queue.ts:96-97`

  ```ts
  Math.min(MAX_CHARACTERS_PER_TICK, Math.max(1, Math.ceil(pendingCharacters / CATCH_UP_DIVISOR)))
  ```

  两个常量都是 24（`:29-31`，含 `FINAL_INK_SETTLE_MS = 230`）：积压 1 字仍逐字，积压越大追得越快，封顶 24 字/tick；终态事件仍排在所有字符之后，代理对（emoji/生僻字）不拆半。
- `src/renderer/components/chat/MessageBubble.tsx:499` 的 Streamdown `animated` 改为恒 `false`，并删掉 `index.css` 中配合它的 `[data-sd-animate]` 覆盖块——逐字队列成为唯一字级动画层。

## 二、首个字不再被供应商计价 HTTP 挡住

**现象**：从「发送」到「首字」之间有明显空窗，网络慢时更像卡住。

**根因**：`agent-runner.ts` 在首个模型请求之前 `await ensureProviderPricing(provider.id)`——那是一次对供应商计价接口、没有 deadline 的 HTTP 请求，只为补齐成本数字，却在关键路径上。

**修复**：`src/main/agent-engine/agent-runner.ts:328` 改为 `void ensureProviderPricing(...).catch(() => undefined)`。成本数字仍由 `conversation-lifecycle-service` 在读取会话时 await 水合，功能不丢，只是不再挡首字。

## 三、timing 上实时行

**现象**：一轮跑完看不到「总耗时/首响应/模型/工具」，必须等 `refreshConversation` 落地或切会话。

**根因**：`done` 事件带着 `timing` 到达 renderer，但 store 追加实时 assistant 行时不写这个字段。

**修复**：`src/renderer/stores/use-chat-store.ts:905` 在 `done` 分支写入 `timing: event.timing`，`TimingSummary` 在轮次结束那一刻即渲染。

## 四、死状态清理，与「停止后文字不要立刻消失」

**现象 / 风险**：①`streamingByConversation.status` 与 `lastActivityAt` 在渲染层**没有任何读取点**，却在 12 处事件分支里被赋中英文混杂的样板文案（`'Running xxx...'`、`'已停止'`），是「进程更新必须中文」改造后的英文泄漏源；`ChatMessage.executionTrace` / `ExecutionTraceEntry` / `execution_trace` 事件同样已整体废弃。②`abortStream()` 把整份 stream reset 成 idle（含 `content`），而取消轮次的落盘行要等 run unwind 之后才写，用户已读到的文字随气泡立刻消失。

**修复**：

- 删除 `status`/`lastActivityAt` 及 12 处赋值、`executionTrace` 与其类型与事件名（全仓已无引用）。
- `src/renderer/stores/use-chat-store.ts:588`（`:605`）：`abortStream()` 只置 `isStreaming: false` 并清 `goalConfirmation`/`toolApproval`，**保留已排空的正文**。
- `src/renderer/components/chat/MessageList.tsx:107` `holdsStoppedStreamCopy = !isStreaming && Boolean(streamingContent)`（渲染点 `:657`）继续渲染该副本，取消轮次落盘后由 `refreshConversation`/`done` 回收。

## 五、失败原因写在「会被显示的那一行」，并可原地重试本轮

**现象**：三条。①失败提示永远是同一句通用文案，真实原因（连不上/限流/鉴权失败/模型名不存在）看不到；②runner 里剩下的失败文案是英文，落在中文界面上不可读；③唯一补救是重新手打同一句提示词，而 `regenerateFromMessage` 只回填正文、不回填该轮的文档附件与引用图，重试等于把附件丢掉。

**根因（①最关键，链路两侧契约相反）**：`userFacingRunError` 只保留错误字符串的**第一行**（落盘的「未完成」提示与界面横幅都只吃这一行），而 `formatProviderRequestFailure` 把供应商原始英文放在第一行、把中文 `排查建议` 排在末尾，于是每条供应商失败都塌缩成通用句——写好的建议没有任何用户能看到。

**修复**：

- `src/main/services/provider-request-diagnostics.ts:26` 新增 `FAILURE_GUIDANCE` 表，按 `ProviderError.code`（`network`/`timeout`/`auth_failed`/`rate_limited`/`model_not_found`/`invalid_request`/`unknown`）给出 `{headline, advice}`；返回值改为「中文原因 + 下一步」打头，供应商原始文本与 `[Request diagnostics: source=…; phase=…; baseUrl=…; code=…; status=…; retryable=…]` 依次排在后面。诊断信息一条没少，只是不再占据会被显示的那一行。
- `src/main/services/assistant-turn-content.ts:7`（`userFacingRunError`，由 `:53` 调用）行为不变，补文档注释把契约写死：**只有第一行会进界面**。
- `agent-runner.ts` 四处失败文案改为中文「原因 + 下一步」：`describeEmptyResponse`、空回复重试补充说明、工具已完成但无最终答案、同一执行器二次启动守卫。
- `src/renderer/components/chat/ChatPanel.tsx:283` 横幅只显示第一行（`error.split('\n', 1)[0]`），完整文本放 `title`。
- 重试入口：`MessageBubble.tsx:57/59` 新增 `showActions`（流式中与「停止后留存副本」为 `false`，它们的 `id` 是合成的 `streaming-*`，引用/复制/收藏会指向不存在的持久化行；渲染门在 `:721`）与 `canRegenerate`，`:726-729` 挂「重新生成」按钮（文案 `:569-572` 的 `actionCopy.regenerate`，三语齐）；`MessageList.tsx:329` 计算 `latestReplyMessageId`，`:572` 只给最新一条持久化 assistant 行开启；`use-chat-store.ts` 的 `regenerateFromMessage` 在回填正文之外一并回填 `referenceImages` 与 `documentAttachments`。顺带删掉从未被读取的 `executingTools` prop 与 `remove`/`confirm` 两对无渲染点文案。

## 六、执行计划改为可打勾清单（气泡与右侧任务便签同源）

**风险**：改造前 `plan` 块只是一段多行文本，`step` 汇报不指向任何条目，界面**没有可信依据**把某条 step 归给某个计划项——只能按出现顺序猜，一旦模型乱序、重复或补发步骤就会打错勾，计划也就只能当正文铺在气泡里。

**修复（协议 → 落盘 → 派生 → UI → 提示词）**：

1. **协议**：`src/main/ipc/progress-protocol.ts` 提取改为**先捕获整个属性袋再分别读 `kind`/`item`**（`:99` `progressItemAttributePattern`、`:122-123`），属性顺序无关，`<eva-progress item="2" kind="step">` 不再因顺序被整条丢弃；两个 strip 正则本就容忍任意属性袋（`:85` `PROGRESS_TAG_KINDS` 单点派生）。`item` 缺失或 `<=0` 视为无编号。
2. **类型与落盘**：`ProgressUpdate.item?`、`ChatMessage.progressItem?`、`ChatStreamEvent.progressItem?`；`src/main/ipc/conversation.ts:1251` `publishProgress(kind, content, item?)` 用条件展开写三个载体（持久化行 `:1271`、`CHAT_STREAM` 事件 `:1284`、内存 `progressUpdates`），无编号时不写 `undefined` 键。落盘仍是既有的 plan/step 行，刷新后清单可完整重建。
3. **派生层（纯函数）**：从 renderer 移到 `src/shared/plan-checklist.ts`——`tsconfig.node.json` 不允许 main 进程 import `src/renderer`，而 ACP 门面要投影同一份清单。`splitPlanLines`（`:33`）逐行剥掉模型自带的 `-`/`1.`/`（1）` 标记；`buildPlanChecklist`（`:48`）规则：plan 行即条目 → step 的 `item` 在范围内且未勾则勾它，否则消费下一个未勾项 → 无未勾项可消费则计 `overflowStepCount`（`:66-68`）→ 第二个 plan 块视为改版，`revised = true` 并重置清单（`:58-60`）。没出现过 plan 时返回 `undefined`。
4. **UI**：新增 `src/renderer/components/chat/PlanChecklist.tsx`（`:15`），三态图标 done `#059669` / active `#7c3aed`（**仅流式中才有 active**）/ pending `#d4d4d8`（`:47-50`），序号由界面生成且 `aria-hidden`（`:51`），头部标题带「（已调整）」（`:34`），底部「另有 N 步汇报在计划之外」（`:58-59`）。气泡内在 `ProcessReportsView`（`MessageBubble.tsx:355`）里用 `feed.checklist` 分支替换原计划文本卡（`:360-366`，无清单时仍回落到 `:367` 的旧 plan 行，`renderItemText` 继续走 `ProgressMarkdown` 以保持「计划与正文同字号同偏好」），右侧便签挂同一组件（`TaskWorkspacePanel.tsx:29/182/599`）；便签在 `isStreaming` 时只取本轮 live `progressUpdates`，避免上一轮已完成态冒充本轮进度。CSS 新增 `.plan-checklist*`，计划框保留 violet 左边与浅底，气泡宿主标题延续 violet-600。
5. **提示词**（`detailed` 分支）：`src/main/agent-engine/context.ts:438-439`——计划每行即一个条目、由界面编号（明令 "do not add your own numbering"），step 必须写成 `<eva-progress kind="step" item="N">` 且 `item` 为它刚完成的行号，工作偏离计划时改发新 plan 块（清单重置），且「不得靠复述计划打勾」。
