## 背景

用户当日提出三个反馈，指向同一层：**执行过程怎么显示、权限怎么放行**。

1. 「明明开了全部权限，执行命令时还是问我。」
2. 「加载半天、中间什么都不说，最后一次性给结论。」
3. 对"过程区"的定位做了明确澄清：过程区的主角**不是模型的原始思考**，而是**每一步的汇报**——"就像给领导汇报"：打算做什么/为什么 → 做完结果如何 → 下一步。原始思维链"给领导看会很乱很杂"；工具调用情况**不需要突出**，因为用户并不关注工具怎么调。

本文档记录**执行过程的呈现方式**与**审批交互**这一侧的改动。同一批工作里"答复内容与执行正确性"的另一半单独成文：`2026-09-22-回复链路与运行时修复-开发记录.md`。

## 一、审批不再白问：会话豁免 + 策略开关（P1）

### 根因

用户的第一条反馈来自一个被两条**正交权限轴**混淆的设计：

- `ConversationPermissionLevel`（`workspace` / `granted-folders` / `full-access`）只放大**文件系统范围**，与弹窗无关；
- 是否弹窗**只由** `automation.toolApproval.policy` 决定，本机 `config.json` 的 `automation` 里**根本没有 `toolApproval` 键**，于是落到默认 `safe`。

同时 Settings 的自动化页只暴露了 `sandbox.level`，**没有任何地方能改审批策略**。并且卡片上的「本会话内都允许」是**空操作**：`CHAT_TOOL_APPROVAL_DECIDE` 把 `rememberScope` 写进活动日志字符串后就不再使用，全仓也没有会话级豁免缓存。

### 修复

1. `tool-approval-policy.ts` 新增按「会话 + `ApprovalCategory`」记账的会话豁免注册表。`PendingApproval` 记录类别；`resolvePendingApproval` 增加第四个参数 `rememberScope`，**仅在批准且 scope 为 `session` 时**写入豁免；`createLocalToolApproval` 在弹窗前先查豁免；新增 `clearSessionApprovals`。
2. `conversation.ts` 的 `CHAT_TOOL_APPROVAL_DECIDE` 透传 `rememberScope`（原先只用于日志），`CONVERSATION_DELETE` 清理该会话豁免。app-server 的 `APPROVAL_DECIDE` 同样透传。审批策略是**全局设置**，不随对话切换。
3. `conversation.ts` 与 `SettingsDialog` 的 `automation` 装配改为**逐字段合并** `toolApproval`/`sandbox`——此前浅层 spread 会让存储里的半截对象顶掉默认值（`toolApproval` 缺 `timeoutMs` 时审批计时退化成 `undefined`）。
4. Settings 自动化页新增「工具审批」下拉（`off`/`safe`/`strict`/`paranoid`，含逐档说明），写入 `automation.toolApproval.policy`；`ui-copy.ts` 补 en/zh/ja 三语文案。审批卡片的会话按钮改为「本会话内都允许「<类别>」」，把**生效范围写在按钮上**。
5. `tool-approval-policy.ts` 另按会话**串行展示**审批卡（`displayedApprovals` + `approvalWaiters` FIFO），前一张结束（批准/拒绝/超时/中断）后才递补下一张；并行工具批次不再同时发多张卡片（渲染层只支持一张，先到的会顶掉后到的）。`rejectAllPendingApprovalsForConversation` 供中断/超时清理；新一轮 `CHAT_SEND` 也会释放上一轮遗留的审批槽位。

### 验证（含真机）

- 单测 `tests/unit/tool-approval-policy.test.ts`（19 项通过，新增 6 项：同类别同会话免询问、`once` 不豁免、不跨类别、不跨会话、拒绝不豁免、会话删除后失效）。
- 真机（CDP 驱动运行中的应用，探针会话用后删除）：
  1. 审批卡 2.0s 出现，类别「终端命令」，按钮文案与 title 为「本会话内都允许「终端命令」」/「本会话内不再询问「终端命令」类操作」。
  2. 真实 DOM 点击会话按钮后：`chat.tool_approval_requested` 1 次、`chat.tool_approved`「(session)」1 次、`execute_command` 执行 1 次。
  3. 同会话第二条 `execute_command`（`node --version`）：**未出现审批卡**；`tool.started` 累计 2 次而审批请求仍是 1 次——豁免按会话生效。
  4. 同会话再要求 `write_file`：**仍然弹卡**（类别 `workspace-write`），审批请求 1→2——豁免按类别隔离，不放大成"整会话放行"。
  5. 设置 → 插件页 →「工具审批」下拉存在，显示生效值 `safe`，四档文案正常。

## 二、执行过程实时可见（P0）

### 现象与根因

用户的「中间什么都不说」来自两处叠加：

- 用户当时的 Coding Assistant 智能体是 `processOutput: 'off'` + `showThinking: false`，`publishProgress` 在 `conversation.ts` **首行即 return**，进度既不产生也不落盘；
- 即便不是 `off`，`isStreamedSynthesisHidden` 也会在**出现工具调用后隐藏全部流式正文**直到 `done`。工具组默认折叠，`thinking` 事件只被当作一句 status。

### 修复

1. **删除 `isStreamedSynthesisHidden`**：有工具调用时不再隐藏流式正文，`MessageList` 始终渲染 `streamingContent`。
2. `use-streaming` 的逐字节奏判据改为新的 `isStreamedTextRendered`（正文确实在渲染才放行；本轮回复行已显示同一段文本时一次性吐出），保住原守卫"不为不可见的动画推迟 `done`"，而不依赖"隐藏正文"这个前提。
3. `MessageBubble` 的 `TimelineToolGroup` 在 **`streaming` 期间默认展开**，轮次结束后回到摘要；`.execution-feed__timeline` 保持 `max-height: 240px` + 内部滚动。
4. 本机 `agents.json`：Coding Assistant 由 `processOutput: 'off'` / `showThinking: false` 改为 **`'detailed'` / `true`**（改前备份到系统临时目录）。`AgentStore.readAgents()` 每次从磁盘读取，因此正在运行的应用下一条消息即生效。内置种子 `BUILT_IN_AGENTS` 未带该字段（默认 `compact`），未改动。

### 验证

- `npx vitest run tests/unit/chat-stream-store.test.ts tests/unit/stream-reveal-queue.test.ts`（30 项通过，新增 4 项覆盖 `isStreamedTextRendered` 的四种判定）。
- 真机：9026ms（`isStreaming` 为真）时流式正文已在 DOM（64 字），工具轮 9444ms 起、25606ms 结束，**整段工具执行期间该正文持续可见**；工具行 `aria-expanded="true"`（流式期间默认展开）。

## 三、执行过程重排：步骤汇报为主、工具为辅、原始推理深藏（P1）

### 用户要的形态

- 每一步的汇报，像给领导汇报：**打算做什么/为什么 → 做完结果如何 → 下一步**；
- 与**正文同字号同规格**、以**中文为主**；
- 工具调用**不那么突出**；
- 节奏是"**先给计划、再逐步推进、随时调整**"，而不是"一次思考配一次工具调用"；
- 原始推理**保留但深藏**（不自动展开、置于过程末尾）。

### 诊断出的三条硬约束

1. **用户看到的英文不是界面串。** 运行期英文（`Running xxx...`、`Preparing the response...`）写进 `stream.status`，而 `status` 在整个渲染层**没有任何渲染点**（已全量 grep 确认）。所以本地化界面串没有意义——用户看到的英文只来自模型原始推理，**必须从模型侧约束语言**。
2. **计划必须走 `<eva-progress>` 标签。** `isAnswerLikeContent` 把编号列表 / 标题 / 表格 / 代码围栏 / ≥220 字判为正文，`text_reset` 时塞进 `answerPrefixSegments`，直到 `done` 才随正文出现。以编号列表形式写的计划若走自由文本会被**藏起来**。
3. **现有标签管线会把计划压平。** `summarizeExecutionText` 把 `\s+` 归一成空格，`splitExecutionSegments` 再按句切段并在 280/140 字处硬切，多行计划会变成一行、还可能被切碎。

### 修复

**提示词（`context.ts`）**

- 在 `off|compact|detailed` 分支**之前**插入语言规则：进程更新必须与用户语言一致，禁止英文样板、工具名、模型名、内部生命周期文案（`off` 无进展输出，不受影响）。
- `detailed` 分支改为"一个计划块 + 每次有意义的进展一条 step 汇报"协议：开头**恰一个** `<eva-progress kind="plan">`（2–5 条单行步骤，各写做什么与为什么）；此后每个有意义的进展发一条 `<eva-progress kind="step">`，写清做了什么、具体结果（文件/路径/命令/数字/验证状态）、下一步；由**界面编号**，模型不得自行编号、不得复述计划、不得念工具名、不得发无新信息的 step。
- `compact` 的「at most three」与 `off` 的原文**保持不动**。

**协议层（新增 `src/main/ipc/progress-protocol.ts`）**

- `ProgressUpdateKind` 增加 `'plan' | 'step'`。
- `PROGRESS_TAG_KINDS`（`thinking|finding|action|issue|plan|step`）是**唯一的 kind 清单**：提取正则与 `done` 分支的两个 strip 正则都由它派生。这是本次的最高风险点——新增 kind 若不同步，原始 XML 会漏进最终答复。
- `normalizeProgressBlock` **保留换行**（只折叠水平空白与 3+ 连续空行），`plan`/`step` 各用 **700/900** 的长度预算且**不再分段**（一段标签 = 一条持久化行 = 一张卡）；legacy kind 仍走 `splitExecutionSegments` + `summarizeExecutionText`。
- `conversation.ts` 改为从该模块导入（`stripProgressBlocks` / `unwrapProgressTags` 取代原先内联的两个 strip 正则）；若模型把答案裹在标签里，strip 后为空时改用 `unwrapProgressTags` 保留标签内文本，避免清空真实回复。
- `isAnswerLikeContent` **未改**：不打标签的计划仍会被视作正文，作为已知限制。

**渲染层（新增 `src/renderer/lib/process-report.ts`、改 `MessageBubble.tsx` 与 `index.css`）**

- `buildProcessFeed` 过滤内部生命周期行、把 `plan` 从序列里**提升置顶**、只对 `step` 编 1..n 序号（单条持久化行用 `numberSteps: false`，否则会误标"第 1 步"）；`processReportLabel` 给出 `执行计划` / `第 N 步` / `步骤汇报` 与 legacy 文案。
- 计划块与步骤卡外层用 `chat-message-markdown` + 与正文**同一套 markdown 偏好**渲染（因此永远跟随该智能体的字号/配色/字体偏好）；计划块加 violet 左边 + 极浅底，读起来是"文档块"而非"元信息行"。
- 工具行整体降权：标题/详情/图标降为 12px 灰、状态图标 `h-3 w-3`；`TimelineReasoningGroup` 删除。
- 原始推理：`ReasoningPanel` 恒为 `open={false}`，标签改「模型原始思考」（流式中「思考中」），样式降为 zinc 系小字，保留 `max-h-56 overflow-auto`。
- `ExecutionFeedView` 顺序固定为 **步骤汇报 → 工具行 → 原始推理（永远最后）**。
- `ToolCallView.tsx` 同步降权，并把本次触碰到的英文串 `{n} sources` 改为 `{n} 个来源`。

- 新增测试覆盖：detailed/compact/off 三档提示词分支与语言规则、plan/step 提取与多行保真、plan/step 长度预算、凭证脱敏、strip 对所有已登记 kind 生效、`unwrapProgressTags` 不把真实回复清空、计划置顶与只对 step 编号、生命周期行过滤、标签文案、store 与 collapse 里 plan/step 整条保留且按原序附着。

## 四、`dev:debug` 启动脚本（验证基础设施）

### 背景

真机端到端验证需要 Chromium CDP，但 `electron-vite` **只在启动时**接受 `--remoteDebuggingPort`，而桌面启动器 `scripts/start-dev.ps1` 走的 `npm run dev` 不传该参数；`src/main/index.ts` 与整个 `src/` 也没有 `openDevTools`/`toggleDevTools`，应用内没有 DevTools 入口。

### 变化

`package.json` 新增 `dev:debug` = `electron-vite dev --remoteDebuggingPort=9222`；日常 `dev` 脚本与启动器**保持不变**。需要端到端验证时用 `npm run dev:debug`，再经 `http://127.0.0.1:9222/json/list` 取应用页目标（url 含 `5173`）。

### 探针使用注意（实测踩到的坑）

- 应用**最小化**时只做 `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` 不够，`document.visibilityState` 仍是 `hidden`，必须 `ShowWindow(SW_RESTORE)`；hidden 会把渲染层定时器节流到 1s 级，逐字显示几乎停摆、探针会误判。
- 窗口被其他窗口遮挡（`IsIconic=False, visible=True`）也会让 `visibilityState` 为 `hidden`。
- 渲染根是 `src/renderer`，动态导入模块要用 `/stores/use-chat-store.ts` 这种**无前缀** URL（`/src/renderer/...` 会 404）。
- 设置面板渲染的是 `section.settings-page` + Tabs，**没有** `[role="dialog"]`；「工具审批」在**插件**页内，默认 general 页看不到。
- 直接调 `window.eva.chat.send` 会绕过 store，使 `streamingByConversation[id].isStreaming` 卡在 `true`，后续 `sendMessage` 静默早退；探针应走 `selectConversation` → `setInputText` → `sendMessage(agentId)`。
- `Runtime.evaluate` 的 `awaitPromise: true` 在本应用页上常返回 `Promise was collected`；改用"同步 IIFE 启动异步、把结果写到 `window.__probeN`、第二次 evaluate 读取"的模式。
