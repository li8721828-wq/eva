## 背景与约束

13:57 用户问「能让 eva 接入 ACP 通信的能力吗」，14:49 澄清动机：「做 ACP 的 stdio，因为我在手机上面有个 ACP 的通信终端……我做了一个 agent 终端在手机上，现在需要连接 eva」。15:42 用户给出终端侧（Dart/Flutter，`D:\agent_terminal\app`）的硬约束：

- 终端只有一个 WS Transport 实现；**JSON-RPC 响应必须和通知走同一条入站流**，否则在途请求永久挂起；
- 在现有 http server 上挂 upgrade 分支，一条 text frame 装一个完整 JSON-RPC 2.0 对象，binary frame 忽略，子协议不填；
- 联调期希望关掉 Bearer token（终端凭据解析还没落地）；
- **必须回 `initialize` 的 result**，终端等它才算连上；
- `thread/*` + `turn/*` 需映射成 ACP 的 `session/*` + `session/update`，这层是主要工作量；
- 并问 Eva 现在绑 `127.0.0.1` 还是 `0.0.0.0`。

## 一、结论先行：缺的不是传输，是 ACP 语义门面

核对源码后的两条判断，直接改变了工作量分布：

- Eva **不是** stdio-only。它已经是 loopback JSON-RPC 服务（`POST /v1/rpc` + `GET /v1/events` SSE），因此**不需要 bridge 进程**，用户担心的那条最重分支不存在。绑定地址是硬编码 `127.0.0.1`，`loopbackOnly: true` 保持字面量类型不动。
- 缺的是门面：Eva 的方法名是 `thread/*` + `turn/*`，事件集对 ACP 客户端是有损子集，终端要的是 `session/*` + `session/update`。
- 网络路径推荐 `adb reverse tcp:<port> tcp:<port>`：手机连接在 PC 侧落地，Eva 保持 loopback 绑定，零对外暴露。**因此也没有绑 `0.0.0.0`**（附带更正：绑 `127.0.0.1` 时 Tailscale 走不通——远端连接落在 `100.x` 网卡上；`adb reverse` 能通是因为连接终止在 PC 本机）。

## 二、传输层：一条连接一条串行写队列

回应「响应和通知必须同一条流」这一条硬前提。

`src/main/services/app-server/rpc-connection.ts`：

- 所有出站帧（响应、通知、Eva 主动发起的请求）都经由唯一的 `send`→`options.write`（`:163-172`）离开，结构上不可能出现响应与通知分叉。
- **两个 id 空间**：入站 request id 只在回响应时原样带回、绝不查表；Eva 出站 id 由本类生成且带前缀 ``eva:``（`:127`），避免与客户端自选的数字 id 撞号。
- `receive`（`:67`）永不 reject：非法 JSON → `-32700`（`protocol.ts:39`），非 2.0 信封 → `-32600`，未知方法只对**请求**回 `-32601`（`:94-102`，通知无人等待故忽略）。
- `settlePending`（`:141-154`）把「存在但畸形的 `error`」也判为失败——否则一条垃圾回包可能满足掉一个未被答复的权限请求。
- 只做对象 ↔ frame 编解码，不 import `ws`，签名为 `write: (frame: string) => void`，便于单测直接喂字符串。

## 三、`/acp` 门：挂在既有 http server 上

`src/main/services/app-server/acp/index.ts`：

- `registerAcpUpgrade(server, deps)`（`:41`）用 `new WebSocketServer({ noServer: true, perMessageDeflate: false, maxPayload: 1_048_576 })`，`server.on('upgrade', …)`；由 `server.ts:605` 在 `listen` 之前挂上，`stopAppServer` 侧 `acpGateway?.close()`（`server.ts:642-643`）。
- 准入判定 `readRejection`（`:65-81`）：非 `/acp` 路径 → `421`；非 websocket upgrade → `400`；`requireAuth` 时 `authorization` 必须等于 `Bearer <token>` 否则 `401`；**`requireAuth` 关闭时，带 `Origin` 头的升级一律 `403`**。
- **不回填 `Sec-WebSocket-Protocol`**（客户端没发，回一个只会改变它要接受的东西）；`isBinary` 帧直接忽略（`:110-115`）；`close`/`error` 走 `connection.close()` + `acp.dispose()`（`:116-130`）；连接与断开各写一条活动日志（`app_server.acp_connected` / `acp_disconnected`）。

`server.ts:657-661` `resolveListenPort`：先试配置里的 `preferredPort`（整数且 1024–65535 且空闲），否则回落 `findFreePort(49152, 60999)`——`adb reverse` 需要稳定端口。

## 五、审批：让手机可见可答，且永不 auto-approve

**改造前的硬障碍**：`createLocalToolApproval` 唯一出口是 `window.webContents.send`，而 app-server 传的是「第一个未销毁的 BrowserWindow」——手机既看不到也答不了审批，agent 会卡在审批队列里。

- `src/main/services/tool-approval-policy.ts:268` 引入 `ApprovalRelay = (approval) => boolean`，`:270-275` 按 `conversationId` 登记/解除（`setApprovalRelay`）；relay 返回 `false` 表示卡片送不出去，就地按**拒绝**处理。`:254-258` 的 `headlessMode` 契约同样限定：只有 `policy: 'off'` 时才允许 auto-approve（默认推导在 `:333`）。
- ACP 侧 relay：`acp/connection.ts:78-112` 通过 `connection.request('session/request_permission', …)` 发出，选项为 `allow_once` / `allow_always` / `reject_once`，Eva 的 `approvalId` 放在 `_meta`；回包 `outcome === 'selected'` 且 `optionId` 以 `allow` 开头才算批准，`allow_always` 映射为 `rememberScope: 'session'`；**Promise 被拒（超时/断线）时按拒绝处理**（`:106-109`）。
- 归属规则：**谁发起本轮，谁拥有本轮审批**。`session/prompt` 开始处 `setApprovalRelay`，`finally` 解除（`:173` / `:249`）。
