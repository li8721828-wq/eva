## 一、现象：事件到了，卡没画出来

第 1、2 轮真机跑同一个探针提示（「用 skill-creator 新建一个全局技能 probe-skill-write……不要用 execute_command」）。`chat:stream` 侧一切正常：

```
17:05:18  tool_call_start        tool=write_skill_file
17:05:18  tool_approval_request  approval="Write skill file probe-skill-write/SKILL.md"
17:06:18  —— 60.0 秒后 ——
17:06:18  tool.completed         status=error  "Error: Approval timed out after 60s."
```

`%APPDATA%\eva\activity-log.json` 里这两轮共 8 条记录（`tool.started` / `chat.tool_approval_requested` / `chat.tool_approval_timeout` / `tool.completed`）逐条对得上，两轮的时间差都**正好 60 秒**。

**卡就是没画出来。** 第 2 轮结束时 `live.mjs` 抓了一次 DOM：`hasSummaryText` 的定义是 `document.body.innerText.includes('Write skill file')`，实测为 **false**——摘要文本在整个页面正文里都找不到。驱动脚本按「按钮文本严格等于 `允许（本次）`」在全页找可点按钮，四轮的结果都是 `clicks: []`（第 1 轮当时还没加 DOM dump，那条证据只有第 2 轮有）。也就是说：**事件确实进了渲染进程，卡一张都没出现**，这次调用只能在 60 秒后被自动拒绝。

## 二、根因：拿「回合是否还在流」当闸门，是第二次

`src/renderer/stores/use-chat-store.ts:770` 的 `case 'tool_approval_request'` 原本带着：

```ts
const existingStream = s.streamingByConversation[conversationId]
if (existingStream && !existingStream.isStreaming) return s
```

而带工具的轮次时序是：模型产出带 `tool_calls` 的那一轮 → 该轮**自己收尾**（`done`，`isStreaming` 归 false）→ 落盘中间那条助手行 → `ToolDispatcher.dispatch()` 才去 await 用户点击。**审批事件到达时 `isStreaming` 早就是 false 了**，守卫于是把事件丢弃，主进程白等 60 秒。

这正是 10-15 在 `ask_user_request` 分支上修掉的同一条守卫、同一个原因（当天 CHANGELOG 第三条把它记为「真机抓到的第二个缺陷」）。差别只在于：审批这条链路**从来没有一条覆盖这个时序的测试**，所以它一直带着这个 bug 活着——`git log` 上看不出来，单测全绿也照样错。

## 三、修复：删守卫，并把时序写进注释

改成无条件收卡，与其余所有 live 事件分支一致；同时把「为什么这里不能有守卫」写进代码注释（这类缺陷的复发概率取决于下一个人是否知道这个时序）：

```ts
case 'tool_approval_request': {
  if (!event.toolApproval) break
  set((s) => {
    // No streaming check here: the round that produced the tool call writes
    // its own assistant row and settles the stream before dispatch waits for
    // the click, so isStreaming is already false when this lands. Keeping a
    // guard here would hide the only card the call can be approved from and
    // let it auto-deny at 60s — the same defect `ask_user_request` had.
    ...isStreaming: true, toolApproval: event.toolApproval
  })
}
```

收卡的同时把 `isStreaming` 置回 true：卡片还挂在界面上，这一轮在用户视角就是「还没结束」，中止按钮必须还在。该清卡的两个出口没动——abort 清、`decideToolApproval` 回填后清。

**先红后绿**：`tests/unit/chat-stream-store.test.ts` 新增一组「tool approval card state」，用一条真实的挂起审批 fixture（`category: 'workspace-write'`、`summary: 'Write skill file probe-skill-write/SKILL.md'`）驱动 store。17:09:28 写测时它是红的（17:09:45 删守卫后转绿）——复现测的价值就在这条时间差上，否则它和其余 794 项一样会绿着放过这个 bug。

## 四、真机取证：跑了什么、证到哪、被什么挡住

实例归属：`npm run dev:debug`（9222 + 5173）跑的是**上一段会话 10-15 19:50 起的实例**，进程链 bash → npm run dev:debug → electron-vite → electron 可追认，因此才自行重启（重启他起的实例属破坏性动作，未做）。重启的原因是一手事实：**改 `src/main/**` 不会让这个 dev watcher 可靠重建主进程**——16:42 改了 `skill-service.ts`，16:5x 在 `out/main/index.js` 里对新符号 0 指纹；停掉（按 PID 与 CommandLine 校验匹配，只杀 electron.exe 122856，其余已自行退出）、16:54:10 重新构建后，`write_skill_file` 在产物里出现 5 次。渲染层改动走 vite HMR，不需要这一步。
