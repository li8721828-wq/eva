# 回复链路与执行过程修复开发记录

日期：2026-09-10
版本：0.1.205

## 变更范围

本次修改集中在对话回复链路的三处正确性修复（只读缓存、上下文预算、错误状态码）、ReAct 执行循环的两处行为改进（单读收尾、重复批次门），以及执行过程块在消息内的显示顺序。不改变工具权限模型，不涉及排版规范与用户偏好档。

## 一、写后重读拿到旧内容（只读缓存永不失效）

### 现象

模型"改完文件、再读同一路径验证"时读到的是**修改前**的内容，进而在写入验证清单里被当成"已验证"，把未生效的改动汇报为完成。

### 根因

`readOnlyToolCache` 在整个 run 内只写不删：缓存键是"工具名 + 参数"，写入/编辑之后用相同参数的读取（整文件读是最常见形式）会直接命中旧结果，且不会因文件已变化而失效。

### 修复

- 新增 `LOCAL_FILE_READ_TOOL_NAMES`（`read_file` / `list_directory` / `search_files`）与运行级 `workspaceRevision`（agent-runner.ts:317）。
- 本地读取的缓存键带版本号（`rev{n}:…`），网络读取保持原键，互不影响。
- 成功的 `write_file` / `edit_file` / `execute_command` 以及 `spreadsheet` 的 `create` / `update` 递增版本（agent-runner.ts:687），此前缓存的本地读取立即失效。
- 效果：写后验证的 `read_file` 一定重新执行，不会再拿旧内容当"验证通过"。

### 验证

- 新增回归用例"re-reads a file after a successful write instead of reusing the cached pre-edit content"，并做过变异验证（去掉版本号后该用例失败，读取执行次数 1 vs 2）。
- 应用内实测：探针会话中 `read_file alpha.txt` 返回 `version=1` → `write_file` → 重读返回 `version=2`，磁盘内容一致；修复前第四步会命中缓存返回 `version=1`。

## 二、预算坍缩：工具定义撑爆预算时整个请求被静默丢弃

### 现象

当 Agent 启用的工具定义（例如挂载了几十个 MCP 工具）超过模型输入预算时，发给供应商的请求里用户消息、历史全部消失，只剩一条被截断到 2 个字符的 system 消息，且不报错。

### 根因

`context.ts` 的 `fitMessages` 用 `maxTokens - toolDefinitionTokens` 调 `trimMessages`；预算被工具定义吃光后 `remainingBudget <= 0`，退化分支只返回被压缩的 system 消息。系统提示词单独超预算时同理，最新请求会被静默丢弃。

### 修复

- 工具定义本身就超出输入预算时，`fitMessages` 直接抛出可操作的错误：说明需要多少 token、预算是多少、建议减少工具或更换更大窗口的模型（context.ts:251）。`fitMessages` 的调用点都在 AgentRunner 的 try/catch 内，会转化为正常的 error 事件。
- `trimMessages` 的退化分支改为：一半预算（`FALLBACK_SYSTEM_BUDGET_RATIO = 0.5`）留给压缩后的系统提示词，其余留给最新的一组消息（context.ts:289-299），用户当前请求不再被静默丢弃。

### 验证

- 新增 3 个单测：系统提示词独自超预算时保留当前请求；工具定义挤占预算时保留最新请求；工具定义直接超预算时明确报错。
- 应用内实测：临时供应商（上下文窗口 4096）+ 23 个工具的 Agent，工具定义实测 5064 token，应用返回 "Tool definitions require about 5064 tokens but this model's input budget is 4096 tokens…"，不再发出没有用户提问的空请求。

## 三、供应商错误状态码丢失（诊断恒为 status=none）

### 现象

`[Request diagnostics: …]` 里 HTTP 状态恒为 `status=none`，401 / 429 / 400 等真实状态无法区分。

### 根因

`classifyError` 读取了错误的 `status` / `statusCode` 用于分类，但分类结果 `ProviderError` 上没有保存状态码，诊断层只能拿到 undefined。

### 修复

- `ProviderError` 新增可选 `status` 字段（errors.ts:3）。
- 新增 `readHttpStatus`：兼容 `status` / `statusCode` 以及字符串形态（errors.ts:69）。
- `classifyError` 拆为"分类 + 回填 status"两步（errors.ts:83、92）。

### 验证

- 新增 2 个单测（保留导致失败的 HTTP 状态；失败不带状态时不设置）+ 1 个诊断格式用例（`status=401`）。
- 应用内实测：用不存在的模型名触发真实供应商错误，诊断行为 `code=auth_failed; status=401`。

## 四、单次只读即收尾改为无工具检查点

### 现象

普通对话里模型一轮只发一个"快读"调用（`read_file` / `read_terminal` / `read_web_page` / `inspect_runtime`）且成功时，循环立刻跳出转最终总结。"先读再改"类请求（读 A → 改 A）会被截断成纯文字回答，修改不会发生。

### 根因

单读场景曾有一条"读一眼就直接回答"的快路径，用硬 `break` 收口，没有区分"读完就答"和"读完还要动手"两种情况。

### 修复

- 单读成功后不再硬 break，而是发起一次**无工具的 FINAL/CONTINUE 自决检查点**（`LONE_READ_CHECKPOINT_PROMPT`，agent-runner.ts:110）：模型回答 `FINAL:` 则收口，回答 `CONTINUE:` 或继续发工具调用则回到循环继续执行（agent-runner.ts:793）。
- 若存在未验证的写入，先补"回读验证"提示而不是收口（agent-runner.ts:797）。
- 接近工具循环上限时直接收口，不额外消耗一次调用。

### 验证

- 新增 2 个用例：单读在检查点直接 FINAL 收口；检查点报 CONTINUE 后继续执行真实动作。
- 应用内实测（真实供应商）："读后要改"场景 → 检查点输出 CONTINUE → `edit_file` 真实落盘 → 验证性重读拿到新内容；"读后只回答"场景 → 检查点直接 FINAL 收口，4.5 秒完成，未改任何文件。

## 五、重复批次中断误伤"写后验证"

### 现象

`read A → write A → read A` 中的第三次读取（写后验证）与第一次同签名，被"重复批次即中断"逻辑拦下，拿不到新内容——恰好把第一条修复挡在门外。

### 根因

`previousNormalToolBatches` 是 `Set<string>`，批次签名只要出现过就 break，不区分工作区状态是否已经变化。

### 修复

- 改为 `Map<批次签名, 记录时的 workspaceRevision>`（agent-runner.ts:345）；批次执行前捕获 `batchStartRevision`（agent-runner.ts:557），仅当记录的版本与批次开始时相同才中断（agent-runner.ts:779-781）。
- 写入/编辑使版本前进后，相同签名的"验证性重读/重跑"视为新的观察，正常执行；供应商无脑重放（状态未变）仍然被拦。

### 验证

- 新增 3 个用例：写后相同批次重跑；未变化时不重复读；未变化时不重复写。
- 应用内实测：写后验证性重读被放行并返回 `version=2`，磁盘内容一致。

## 六、执行过程块移到正文之后

按产品要求调整消息内阅读顺序（MessageBubble.tsx:625-635），现在是：**正文答案 → 执行工具 → token/耗时汇总**；无执行时间线时慢思考面板保持在正文之前。流式期间"工具先跑、正文未输出"时工具块仍在消息顶部，正文出现后追加在其下方。

验证：带 CDP 的真实应用里做 DOM 顺序断言（`markdown-first (OK)`）并截图目检，间距正常；渲染层类型检查无新增错误。

## 使用注意

- 运行中的 dev 应用不会自动重建主进程（`out/main/index.js` 停在启动时刻），主进程改动需完全重启应用后才生效；实测前先用特征串确认新代码已进产物。
- 若模型在小上下文窗口下启用了过多工具，收到"工具定义超出输入预算"的错误属于预期行为，按提示削减工具或更换模型即可，不会再把请求发成空消息。
