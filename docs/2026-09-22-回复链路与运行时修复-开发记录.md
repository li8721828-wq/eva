日期：2026-09-22
版本：0.1.206
分支：develop
状态：改动已在当前工作区落地，**未提交、未发布**

## 背景

今日的主线是"用户提问后到底能不能拿到正确结果"。从用户反馈的两个现象出发——「说『进行改造吧』时工具执行不了」「要求改造代码时收到 `Model deepseek-v4-flash returned an empty response.`」——对整条回复链路做了一次批量审计，逐项定位并修复了会影响最终答复正确性、以及会在用户看不见的地方产生重复副作用的问题。

本文档记录**回复内容与执行正确性**这一侧的改动（工具可见性、空回复、失败/中止落盘、重复执行、串流残留、沙箱与出网边界）。执行过程的**展示方式**与**审批交互**是同一批工作的另一半，单独成文：`2026-09-22-执行过程呈现与权限审批-开发记录.md`。

两条链路（`src/main/ipc/conversation.ts` 与 `src/main/services/app-server/server.ts`）与渲染层的流式收尾是两份文档的共同涉及面，此处只写与"答复正确性"相关的部分。

## 一、工具不再被关键词门控（P0）

### 现象

- 用户说「进行改造吧」「帮我改造这个模块」「把重复逻辑抽出来」时，工具完全执行不了。
- 只有像「修改 src/main.rs」这种**字面带写入动词**的句子才能拿到写工具。

### 根因

1. `selectInitialTools` 用中英关键词正则决定本轮工具**可见性**：写入词表为 `write|edit|modify|create|implement|fix|refactor|patch|delete|rename` 与 `写入|修改|编辑|创建|实现|修复|重构|补丁|删除|重命名`，**不含「改造」**。措辞不命中时，模型只会拿到 `request_additional_tools` 一个工具，连 `read_file` 都没有。
2. `context.ts` 里另有一句**无条件**的 `Do not modify reviewed code unless requested.`，把普通实现类请求也推向"只给方案不改代码"。
3. 由此产生一个误导性结论：看起来像"Agent 配置里没给工具"，实际是门控把工具藏了。

### 修复

- `agent-runner.ts` 不再调用 `selectInitialTools`：`activeToolDefs` 直接取 `allToolDefs`（agent-runner.ts:439）。Agent 配置里授权的工具清单**整体加载**，用哪个工具由模型决定。
- 删除 `src/main/agent-engine/tool-selection.ts`（关键词表、`selectInitialTools`、`expandToolSet`、`REQUEST_ADDITIONAL_TOOLS` 全部移除）；仅把循环逻辑仍在用的 `isFastSynthesisReadTool` 移入 `agent-runner.ts`。
- 退休 `request_additional_tools` 的展开分支；保留"工具不在本 Agent 可用目录内"的兜底，文案改为 `Tool X is not available to this agent.`。
- `context.ts`：`request_additional_tools` 存在时才追加的 "Tools are loaded on demand…" 整段消失；把 `Complete a requested review…` 与 `Do not modify reviewed code unless requested.` 两句并入代码审查那一段，使其只在审查语境生效。
- Goal 步与普通对话的差异此后只保留在**迭代预算**上（`adaptiveToolBudget`），不再有工具可见性差异。

### 验证

- `tests/unit/agent-runner-adaptive-budget.test.ts`（37 项）：首个请求携带完整配置目录且提示词不含 `request_additional_tools`；目录外工具被拒且不执行；首个请求发出全部已配置工具。
- 离线路由核对（临时探针，用后删除）：用 `createToolRegistry()` 解析用户 live 配置里 Coding Assistant 的工具清单，`read_file`/`edit_file`/`write_file`/`execute_command`/`open_terminal`/`write_terminal`/`web_search`/`read_web_page`/`spreadsheet` 全部解析成功。需要应用侧注入可选服务的 `project_search`/`project_index_status`/`manage_personal_preferences`/`delegate_to_model_pool` 因探针未注入而未解析，属探针限制。
- 顺带发现：live 配置里的 `desktop_observe`/`mouse_control`/`keyboard_control`/`desktop_session`/`form_fill_workflow` 五个工具名**在本仓库任何位置都未注册**（全量 grep 无命中）。整体加载后它们仍不会出现，属既有配置漂移，与本次改动无关。

## 二、空回复：先能诊断，再做到重试不是同一个请求（P1）

### 现象与数据

`runtime-runs.json` 里有 16 条 `returned an empty response`，其中 **15 条在 `deepseek-v4-flash`**。run `09b2ddc4` 有两次 `model_call_completed`、`content: ""`（36.3s / 32.2s），期间无任何工具事件——首次调用与那次唯一的空回复重试**都是空的**。同一会话里成功的调用耗时 9–29s 且有正文，指向"与任务难度相关的隐藏推理正在耗尽输出预算"。

### 根因（四点）

1. `openai.ts` 只映射 `stop`/`tool_calls`/`length` 三种 `finish_reason`；网关返回别的值（额度、资源、内容过滤）时被当成正常结束**丢掉**，空回复失去证据。
2. `showThinking: false` 的 Agent 下 Eva 不发送 `thinking` 字段，网关默认开思考、`reasoning_content` 又被 Eva 丢弃，思考占满预算后正文为空；原有 `reasoningHint` 诊断在这条配置下恰是**死代码**。
3. 空回复重试**原样重发同一请求**，必然复现同一结果。
4. 空内容判定排在 `length` 续写判定**之前**，截断型空回复既无证据也走不到恢复路径。

### 修复

1. `ChatChunk` 新增 `rawFinishReason?: string`；`openai.ts` 把非标准 `finish_reason` 记入其中并把 `finishReason` 映射为 `'error'`。标准值不再重复记录——`rawFinishReason` 一旦存在即代表异常结束。
2. `openai.ts` 在 `reasoning.enabled === false` 时显式下发 `thinking: { type: 'disabled' }`（`deepseek` 路由），而不是省略字段任由网关默认生效。
3. `agent-runner.ts` 的 `executeLLMCall` 新增 `options.disableReasoning`，并统计 `reasoningCharacters`（**即使不展示也计数**）；`model_call_completed` 生命周期补记 `finishReason`/`rawFinishReason`/`reasoningCharacters`/`completionTokens`/`contentCharacters`。
4. 主循环与最终汇总的空回复重试都改为"机械上与失败请求不同"：重试前置 `nextCallOverrides = { disableReasoning: true }`，并按是否 `finishReason === 'length'` 追加不同用户提示。
5. 空回复错误改用 `describeEmptyResponse`：输出 `finish reason`、`completion tokens`、隐藏推理字符数，并按 `length`/有推理/带图输入区分可能原因。

### 验证

- `tests/unit/providers.test.ts`（33 项）：`reasoning: { enabled: false }` 确实下发 `thinking: { type: 'disabled' }`；非标准 `finish_reason` 映射为 `error` 且原值保留在 `rawFinishReason`。
- `tests/unit/agent-runner-adaptive-budget.test.ts`：重试改发 `reasoning: { enabled: false }` 并采用第二次正文；双空时错误含 `finish reason: length` / `8192 completion tokens` / `16 characters of hidden reasoning`；汇总空重试同样禁用推理。

## 三、失败轮次不再落盘空回复或半截前缀（P1）

### 风险

`AgentRunner` 的每条失败路径都以 `done {content: ''}` 收尾（agent-runner.ts 的 502/528/566/1078/1111/1129 行）。原持久化条件 `runError && !assistantContent && allToolCalls.length === 0` 只在"无工具调用且无正文"时写入错误提示，于是：

- 有工具调用时落盘 `content: ''` → **空气泡**；
- 有前缀时把工具周期前的**半截前缀当作完整回复**落盘，下一轮会把这段残句当成模型的原回复继续推理。

### 修复

抽出纯函数 `resolveAssistantTurnContent({ completedContent, provisionalContent, runError })`（`src/main/services/assistant-turn-content.ts`）：

- 成功轮次**原样返回**传入内容（不 trim、不改写）——这是唯一决策点；
- 失败轮次保留已完成内容，若为空则退回用户已看到的流式文本，并统一追加"本次回复未完成…"提示；
- `userFacingRunError` 一并移入该模块。

### 验证

新增 5 项单测覆盖：成功原样返回、无内容只落提示、保留半截前缀并标注未完成、退回流式文本、中文诊断首行回显。

## 四、中止落盘去重（真机验证中发现的新缺陷）

### 现象

真机打断验证暴露出"停止落盘"的缺陷：用户看到**正文被完整存了两遍，再加一句停止标记**。

### 根因

中止存在竞态：run 可能已经产出携带完整回复的终态事件，而渲染侧流式缓冲里是**同一段文本**，此时 `completedContent` 与 `provisionalContent` 指向同一次输出，原实现把两者拼接后落盘。
（`agent-run-events.jsonl` 里该轮有 `turn_completed`/`run_completed`、**没有** `turn_interrupted`，据此定位到"中止晚于模型写完"这一窗口。）

### 修复

`resolveAssistantTurnContent` 在中止分支改为"终态内容已包含流式文本时不再追加流式文本"，只保留不重复的部分，并在注释里写明该竞态。停止标记与 `cancelled` 状态语义不变——用户按下停止即视为要停止本轮，即便这轮恰好已写完，也仍标注为已停止、正文只存一份。

### 验证（真机，CDP 驱动运行中的应用）

- 中止时机扫到 `done` 之前 6800ms 命中窗口：`streamedAtAbort: 1332`、`doneBeforeAbort: false`。
- 落盘结果：`executionStatus: 'cancelled'`、长度 1396、停止标记**恰 1 处**、正文未重复、assistant 行数 1。

## 五、汇总恢复阶段不再重跑已执行过的工具调用（P1，副作用）

### 风险

最终汇总阶段的"有界恢复批次"会执行模型在这一阶段返回的任何工具调用。该批次的前提（上下文里已有工具结果）说明这些调用本就是重复请求，因此同一个 `write_file`/`execute_command` 会在工具循环已判定"工具工作完成"之后**被再执行一次**。单测里的"重复写批次"用例原本记录循环内执行 2 次，恢复批次使其变成 **3 次**。

### 修复

run 内新增 `executedToolSignatures`（按参数精确到具体调用的签名），汇总恢复批次只执行"本次 run 尚未执行过"的调用；重复调用连同说明一起回灌给模型（"本次 run 已执行过，结果已在对话中，不要再重试，直接给出最终答案"）。读取类调用不受影响（本就可走 `readOnlyToolCache`）。`name:args` 签名抽成 `toolCallSignature`，供批次重复判定、恢复去重与执行记录三处复用。

### 边界（有意保留）

**只挡重复，不挡首次。** 本 run 未执行过的副作用调用在恢复批次里仍会执行——这是该批次存在的意义（覆盖"先读、再写"这类在汇总阶段才提出动作的流程），保持了改动前的既有能力。

### 验证

新增两项单测：重复调用被拒（写执行 2 次而非 3 次，且回灌文本包含 `already performed them`）、未执行过的调用仍被恢复（写执行 1 次）。把恢复过滤临时改回旧行为后，重复用例以 `expected 3 to be 2` 失败，确认该用例是有效回归防护。

## 六、跨轮串流残留：上一轮的字会漏进新一轮气泡（P0）

### 现象

回复持久化后，字符逐字显示队列仍按 42ms/字符排空（2000 字约 84 秒）。用户在此期间发出下一轮消息时，上一轮的残留文本会通过 `isStreaming` 守卫落进**新一轮气泡**，显示成从单词中间开始的碎片。真实会话 `699ec294` 的消息快照与 `agent-run-events.jsonl` 记录了这一过程。

### 修复

1. 逐字显示队列抽为独立模块 `src/renderer/lib/stream-reveal-queue.ts`（`setRevealSink` 注入 sink，store 只依赖其 `dropQueuedItemsFor`）；新一轮/停止/清空时丢弃该会话残留——队列按**会话隔离**。
2. 主进程把 `done` 事件**推迟到 assistant 行落盘之后**发送，并携带该行 id。
3. store 的 `done` 分支先按 id 判断"回复已在屏幕上"→ 只收尾不重复追加；若该 id 属于**更早一轮**则不打断正在流式的新一轮。

### 验证

- 把 id 分支临时改为恒空后，新增的 3 个 store 测试全部失败，恢复后通过。
- 真机（CDP，真实两轮链路）：3650 字长回复 → 回复刚落盘立刻追问。发出第二轮前队列仍残留 3464 字（正是复现条件），`sendMessage` 后残留归 0，第二轮只出现 1 个流式样本并持久化为干净的"收到"，`leakCount = 0`、气泡数 = 持久化回复数 = 2，无碎片、无重复。探针会话已删除。

## 七、工具周期边界不再吞掉答案段落（P1）

### 现象

ReAct 每个工具周期开始时（`text_reset`），周期前已流式写出的文本会被降级为 thinking 进展卡片并从最终回复中清空。当模型把正式答案的一部分（标题、编号列表等结构化段落）写在调用工具**之前**时，持久化的最终回复**从句子中间开始**，前半部分散落成零碎的思考片段。

### 修复

新增 `isAnswerLikeContent` 判定（标题 / 编号列表 / 表格 / 代码围栏 / 长段落 ≥220 字）。命中时该段文本按顺序并入最终回复（`answerPrefixSegments`），不进入 thinking 进展；协议修复等 `discardProvisionalText` 场景仍按原样丢弃。

### 验证

`npm run typecheck`（node）无错误；全量测试通过。

### 遗留（已在同日修复）

该判定让"以编号/要点形式出现的执行计划叙述"也可能被并入最终回复。这一点在当日后续的"执行过程重排"（见另一份文档）里得到正面处理：计划改走 `<eva-progress kind="plan">` 标签传输，不再依赖自由文本。

## 八、批量修复：沙箱、工具与展示的八个边界（P1）

按审计顺序列出，均在中英混排的同一批提交范围内：

1. **`read_file` 同名兜底静默换文件**：兜底读到与请求路径不同的文件却不告知模型 → 结果前置一行替换说明（请求路径 + 实际路径），避免模型在被静默替换的文件上继续推理。
2. **工具审批名单写错工具名**：名单里用的是**未注册**的工具名，浏览器与若干检索工具因此静默落到"无需审批" → 改为按真实注册名登记，浏览器控制收敛为 `browser_control`。
3. **`write_terminal` 提交的命令未走沙箱判定**：`writeInput` 与面板原始按键共用，判定只挂在 `writeInput` 上会漏 → 在 `submitted` 分支调用 `checkSandboxCommand(text)`。
4. **私网判定误封公网域名**：把 `fc`/`fd` 开头的公网域名当作 IPv6 唯一本地地址 → 收紧前缀识别，区分域名与 IP 字面量。
5. **出网请求无 deadline**：搜索源请求无超时；`Retry-After` 可被服务端放大到任意等待 → 统一 deadline + 重试退避夹取（`MAX_RETRY_DELAY_MS = 30s`）。
6. **沙箱上下文是模块级单例**：`FileService`/`TerminalService` 各自保存上下文，并发 run 会互相覆盖 → 改为按 run 的注册表 `src/main/services/sandbox/scope.ts`（`openSandboxScope`/`closeSandboxScope`/`currentSandboxScope`），**当前最严格的一档生效**，`agent-runner` 在 finally 关闭。
7. **逐字显示队列全局 FIFO**：后台会话的动画会阻塞前台会话的字符输出与新回合 → 按会话隔离（`src/renderer/lib/stream-reveal-queue.ts`）；工具轮隐藏正文时不再按逐字节奏空等。
8. **失败轮次的乐观用户行永久残留 / 系统行被当气泡渲染**：失败或发送 reject 后 `pendingMessageIds` 未清理，没有快照可对账时气泡永久留在屏幕上；被中断回合落盘的 `role: 'system'` 行（含 `<turn_aborted>` 协议标签）被渲染成助手气泡 → `error` 分支与 `sendMessage` catch 清理 pending；`collapseToolHistoryMessages` 跳过 `system` 行。

另有两条属目录遍历边界（第 9、10 项）：

9. **目录遍历只校验起点路径**：搜索/递归列表会跟着 junction、符号链接或挂载点走出授权根（Windows 上 junction 的 `isDirectory()` 为假、`isSymbolicLink()` 为真，已实测确认）→ `FileServiceImpl` 暴露 `resolveAuthorizedPath`，遍历时跳过链接项并对**每个要下沉的目录**重新做一次授权校验；`search-tools.ts` 同步适配。
10. **远程会话 / app-server 路径不广播会话变更**：写入消息后界面不刷新 → 抽出 `conversation-notify.ts` 的 `notifyRendererConversationChanged`，两条路径补齐 `CONVERSATION_CHANGED`。

### 验证

逐项均补了对应单测（沙箱作用域 5 项、逐字队列 8 项、file/web 工具、终端策略、搜索路径边界等）。
